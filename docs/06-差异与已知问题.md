## 四、环境相关（不是缺陷，但会影响判断）

| 现象 | 说明 |
|---|---|
| 改了 `lib/client.js` 页面没变化 | 宿主给三方插件的 client 不带内容指纹，必须**硬刷新**（`Ctrl+Shift+R`）。**软刷新/页签复开不一定换模块**：2026-11-04 出现过“G-15 已同步但球仍显示”的现象，重开页签后自愈——**先判断是不是旧页面，再怀疑代码**；判据是安装副本 `lib/client.js` 的 md5 已更新、且页面加载时间早于同步时间 |
| 浏览器端自动化测试已整体移除 | 那套管道（CDP + 预览页 + minihost）在本机抖动到 3.4s～50s，且多次靠调等待预算掩盖真实缺陷。可静态判定的部分改由 `check-css` / `check-render` 守住；其余靠人工看页面（见 `05` §三点五） |
| 测试实例与主实例共用数据根 | 历史原因，测试会污染主实例数据；跑破坏性测试前先备份或改数据根 |
| `synopkg status` 显示 stopped 但进程在跑 | s6 接管 stdout，判断存活用**端口探测** |
| 直接 `git push` 报 publickey 失败 | 凭据由插件托管，推送走 `git_sluice`/`git_commit_push` |
| 改 `ui/css/*.css` 不重新 build 不生效 | `build.cjs` 把 CSS 内联进 `lib/client.js`，页面用的是产物。**只改源文件跑门禁会假绿**——必须 `node build.cjs` 后再验（2026-11-04 实测：改 `z-index` 为 300 未 build 时门禁仍绿，build 后立刻 EXIT=1） |
| 压缩行为与「80% 才压」的旧认知不同 | 本机装了外部 `dsh-live-compact` 1.0.5：每轮切片 + 反应式引擎被换包，机制与本机证据见 `10` §二～§四 |

## 四点五、架构限制（不是缺陷，设计时必须知道）

| 限制 | 依据 | 后果 | 应对 |
|---|---|---|---|
| dsh 的自动压缩只能按**虚拟模型**申报的窗口算 | `07` §二点六（`routedTarget` 读 `requestHeader().config`；`ConfigureCall` 注释明写不能改路由；`resolveModelInfo` 入参无 session） | 真实目标模型的窗口差异影响不到压缩阈值：按大窗口压 → 切到小模型会爆；按小窗口压 → 大模型被白白浪费 | 申报一个**保守值**（避免 dsh 抛「无容量」错）；真实窗口只在 UI 如实展示 + 切换时提示风险 |
| 「按 session 申报窗口」在 0.2.1 里**没有信息出口**（独立复核过，非推断） | adapter 的 `prepareCall(provider, model)` / `resolveModel(provider, model)` 都没有 session 入参；`LlmCallControls` 只有 reasoningEffort/temperature/maxTokens/stop，**没有 contextWindow 字段**；`sessionId` 在 llm 包里只出现在 `GenerateOptions`（dispatch 阶段，压缩已算完）；压缩**不读** `request/context`（那个事件里其实有 contextWindow，由 agent-loop 写入，但 compaction 另调 `resolveModelInfo` 取值） | 「插件知道该 session 用哪个真实模型」与「能把窗口交出去」之间缺一条接口——时序没问题（压缩确实在发消息时跑），是出口不存在 | 不要试图 hack；唯一「能生效」的办法是伪造 `request/header` 指向真实模型，代价是污染「实际请求配置」记录（agent-loop/ACP/UI 都消费它）且每步会被 `buildRequest` 覆盖回去。若 dsh 将来改为读 `request/context`，这一条即可解除 |
| 上游 `/v1/models` 的容量字段**命名不统一** | 实测 42 个模型：`context_length`、`max_allowed_size`、`context_window.default` 三种并存；3 个图像模型全缺 | 解析逻辑必须按优先级回退，只读一个字段会漏 | 归一化顺序见 `07` §二点六；缺失时不填、UI 显示 `—` |
