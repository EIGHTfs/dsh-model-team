# 06 反代插件化：目录结构与声明式注册

> 定位：反代是可选插件，自己声明能力与路由；model-team 动态发现后按公共契约动态注册。
> 全项目原则：**所有功能都低耦合，插件更必须低耦合**；不得静态依赖某个平台或插件实现。
> 本文是目标契约，不表示当前代码达标。实现缺口见 `13` §二（2026-11-08，基线 `c2f6418`）。

## 一、目标目录

```
src/reverse/                       反代的全部代码都在这一个目录里（域边界）
├── manifest.js                    本域的**声明式清单**（唯一事实来源）
├── register.js                    唯一注册器：读 manifest → 挂载；失败只降级，不抛
├── registry.js                    平台注册表：按清单动态加载实现（top-level await），保持 listPlatforms() 同步
├── driver.js                      平台驱动的域内实现（driverId 与平台列表都来自清单，不写平台名）
├── core/                          平台无关的公共件
│   ├── types.js                   契约常量与形状校验（含身份判据 policy）
│   ├── account-store.js           账号落盘（0600、原子写、按 user_id 判重）
│   ├── login-session.js           设备码登录状态机（平台无关）
│   ├── http-client.js             代理感知 fetcher + 超时（I/O 边界）
│   └── import/                    凭据导入框架
│       ├── index.js               源注册表
│       └── sources/
│           ├── host-credentials.js
│           └── manual.js
├── platforms/                     一个平台一个目录，自包含
│   └── qoder/
│       ├── manifest.js            该平台的声明（driverId/endpoints/capabilities/crypto 后端）
│       ├── oauth.js               设备码 + PKCE 轮询
│       ├── headers.js             Cosy 头族
│       ├── crypto/                native（默认，纯 Node）与 wasm（可选后端）
│       ├── envelope.js            SSE 信封剥离
│       ├── catalog.js             目录 key ↔ 展示名
│       ├── infer.js               一次推理的完整链路
│       └── wasm-path.js           wasm 三档定位
└── routes/                        本域 HTTP（login / accounts / import）
    ├── login.js
    ├── accounts.js
    └── import.js
```

**边界规矩**：反代插件拥有自己的声明与实现，model-team 只依赖公共扩展契约。**有插件就动态发现并按声明注册，没有插件就照常工作**；核心入口不得静态 import `src/reverse/**`。目录分离、动态加载声明内的 handler，都不能替代插件动态发现。现有门禁放行 `reverse/register.js` 的规则仅是过渡状态，仍有 R-01 缺口。

## 二、插件声明与通用注册

反代插件的 `manifest.js` 是该插件的声明来源，model-team 的通用注册器只做「动态发现 → 校验声明 → 注册贡献」。新增插件不得修改核心平台名单或静态路由表。

下例是当前反代声明的节选，不是插件发现接口；完整路由以插件自己的声明与 `02` §二逐条核对。

```js
export const manifest = {
  id: 'reverse',
  // 平台：每个平台自带 driver 描述、加密后端、能力位
  platforms: [
    {
      id: 'qoder',
      driverId: 'reverse-qoder',
      displayName: 'Qoder',                 // 界面只显示这个，不带内部术语
      capabilities: { encryptedInference: true, login: 'device-code' },
      cryptoBackends: ['native', 'wasm'],   // 默认取第一个可用的
      module: './platforms/qoder/index.js',
      inferModule: './platforms/qoder/infer.js',
    },
  ],
  // 路由：声明「路径 + handler 模块」，注册器统一挂载
  // 节选两条导入路由；完整声明还含登录、账号和平台状态接口，见 manifest 与 02 §二。
  routes: [
    { method: 'GET',  path: '/_team/reverse/import/sources',    handler: './routes/import.js#handleReverseImportSourcesRoute' },
    { method: 'POST', path: '/_team/reverse/import',            handler: './routes/import.js#handleReverseImportRoute' },
  ],
  // 导入源：声明启用哪些
  importSources: ['host-credentials', 'manual'],
  // UI 挂载：前端只读这些声明来决定渲染什么，不在前端写平台名
  uiMounts: [
    { slot: 'add-group.auth', kind: 'reverse-account', platformId: 'qoder' },
  ],
};
```

`src/reverse/register.js` 只导出两个函数：

```js
// 挂载：由主插件 apply 调用一次；返回 disposer
export async function registerReverse({ ctx, dataRoot, logger, credentials }) {}

// 能力查询：主流程需要时问它（例如「某平台是否可用」），不问内部实现
export function describeReverse() {}
```

**现有专用调用（过渡实现，不是目标架构）**：

```js
ctx.effect(() => { void registerReverse({ ctx, dataRoot, logger, credentials }); });
```

把调用包进 `effect` 并不消除静态耦合。目标是 model-team 通过通用发现接口消费插件声明，不在入口导入反代专用注册器；R-01/R-02 未关闭前不能标记插件化完成。

## 三、与 model-team 的接缝（只有两处）

| 接缝 | 方式 | 约束 |
|---|---|---|
| 驱动 | 注册器把 `manifest.platforms[]` 交给既有的 `registerReverseDrivers`（内部调用，不经外部文件） | 平台清单只来自 manifest；`drivers/index.js` 不出现平台名 |
| 元数据与 UI | model-team 消费插件声明的认证方式和入口；具体公开出口须先冻结 | 当前 `GET /_team/meta` 仅含 `virtualModel` / `providerIds`，不能写成已有 reverse 段；前端继续改造暂缓 |

**边界（上游错误认领）**：通用层只做两件事——登记认领者、逐帧询问；平台差异（认哪一帧、什么错误码、什么状态）全部写在平台自己的单文件里，由声明里的字符串路径动态加载。通用层不允许出现平台名、错误码表或具体文件路径；反代之外（官方驱动）走同一条路，不存在「只有反代才认领」的特殊分支。详见 `02` §九。

## 五、验收

- 目标门禁：核心没有具体插件静态依赖；插件自己的声明增删无需修改核心；动态加入、移除、再挂载均可观测。
- 现有结构门禁仅拦域外深层 import，放行专用 `register.js` 不等于动态发现或零耦合。
- 隔离副本中验证插件缺失、坏声明、资源缺失和卸载 / 再启用；核心及其他插件必须仍可用。
- 实际文件结构由 `16` 维护；未关闭的实现缺口只在 `13` §二登记。

## 六、路由由谁注册（设计定论）

**定论：反代的 API 路由由 model-team 动态注册，反代自己不做 `webServer.register`。**

| 项 | 规定 | 理由 |
|---|---|---|
| 声明方 | 反代插件声明自己的「方法 + 路径 + handler」及能力；其他可选插件也遵守同一契约 | 插件自己拥有唯一声明，model-team 不另抄清单 |
| 发现方 | model-team 动态发现当前已启用且声明合法的插件 | 不静态 import 反代目录，不硬编码平台名；没有插件就没有该贡献 |
| 注册方 | model-team 的通用注册器按插件声明动态注册 API 与驱动 | 统一传输设施是公共契约，不是具体插件之间的实现依赖 |
| 生命周期 | 插件停用、移除或加载失败只撤销它自己的贡献；再启用重新发现并挂载 | 路由、驱动、导入源和界面入口须成对管理，不能只撤销路由 |
| 门禁 | 验证核心无具体插件静态依赖，并覆盖动态加入 / 移除 / 再挂载和故障隔离 | 当前放行 `reverse/register.js` 的门禁尚不足，见 `13` R-01/R-02 |

> 注册归属以本节为准：**反代插件自己声明，model-team 动态发现后动态注册，没有具体实现耦合**。不得把“路由经过 model-team”解释为“反代必须依赖它的内部传输层”。当前代码仍有 R-01/R-02 缺口，不能声称插件化验收已完成。
