# 19 Qoder 登录流程调研（逐行对照，含行号）

> 目的：把「登录到底该怎么做」按**源码行号**钉死，不再凭印象。
> 记录范围：具体函数的源码行为，不把实现差异直接定性成故障原因。
> Python 配置带 `redirect_uri`，另一实现不带；两者属于不同客户端配置。`machine_id` 的来源也必须读生成函数，不能凭名称断言是系统真实 ID。
> 当前实现逐步对照由 `21` 维护；截图那次登录故障尚未定因，见 `20`。

## 二、我们的实现 vs 参考（差异清单）

| 项 | 我们（`src/reverse/platforms/qoder/oauth.js`） | CN 参考（Python:4458-4462） | 判断 |
|---|---|---|---|
| `redirect_uri` | 由登录 profile 成套选择（`oauth.js:71-87`） | 一份 CN 实现带，另一份不带 | 参数差异，不是已证实故障原因 |
| `machine_id` | 当前通过 `machine-id.js` 解析并持久化 | `4427-4439` 读官方客户端文件，缺失回落 UUID | 与系统 ID 不同；不得把差异当作厂商要求 |
| `client_id` | 当前有三套 profile（`index.js:50-58`） | 不同客户端配置使用不同值 | 需对应真实客户端协议验证，不能自动判对错 |
| nonce | 按 profile 区分带横线 / hex32 | CN / Intl 有不同形态 | 只确认源码行为 |
| 轮询参数 | nonce/verifier/S256（`oauth.js:91-97`） | 对照函数同形 | 参数同形不证明本次请求正确关联 |
| pending 状态 | 当前 404 / 202（`oauth.js:175-182`） | 两份实现有差异 | 已实现，真实响应与落盘仍需关联证据 |
| token 字段 | `token`/`device_token`/`access_token` | 同 | ✅ |
| 用户信息 | `/api/v1/userinfo` | 同 | ✅ |
| 续期端点 | 未实现（M4） | `deviceToken/refresh`；且 **按 token 前缀分流** | 待 M4 |

## 三、实现差异的处理纪律

1. client_id、redirect_uri、授权域及 nonce 形态按同一客户端配置核对，不能任意混合。
2. `machine_id` 先核对真实来源函数；客户端文件 ID、系统 ID、随机 UUID 不是同一事实，不能凭名字替换。
3. pending 判定与 token 解析须用真实响应证明；改过参数不等于完成了登录。
4. 未定因故障不调 TTL、不自动切 profile 碰运气；当前验证缺口见 `20` 与 `06`。
5. 续期不在当前实现中，导入账号不接管他方续期；后续协议须另外冻结。

## 四、仍未解决（需要真机）

- 客户端参数配置仍需对应完整的协议与真实响应验证；不得为排查其他阶段故障自动更换登录 profile。
- Python 的本地 ID 函数读取客户端文件、缺失时生成 UUID，不证明系统 ID 或强制稳定化是厂商要求。当前登录原故障的证据缺口见 `20`。
