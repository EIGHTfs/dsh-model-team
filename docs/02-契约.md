# 02 契约（接口 / 字段 / 事件 / 错误码）

> **唯一契约**。任何文档与本文件冲突，以本文件为准。
> 本文件不解释"为什么"，只写"必须是什么"。设计理由见 `01-需求与不变量.md`。

## 一、总则

| 项 | 规定 |
|---|---|
| 内部端点前缀 | `/_team/`（常量 `API_PREFIX`，服务端 `src/gateway/constants.js`；客户端另存一份并由防漂移用例钉死） |
| 对外入口 | 裸路径 `/v1/chat/completions`、`/v1/models`（**不得加前缀**，否则 DSH 找不到） |
| 请求体上限 | `http.maxBodyBytes`，缺省 8MB |
| 错误响应 | 统一形状见 §七 |
| 认证 | 调用方访问控制由 DSH 承担；群的凭据保留引用，认证方式由所选驱动 / 插件声明，不能把所有来源都按 API Key 处理 |
| 功能边界 | 所有功能低耦合，只消费公开契约，不读其他功能的私有状态或存储 |
| 插件接入 | 可选插件自己声明能力与路由；model-team 动态发现、动态注册和注销，不静态依赖具体插件；目标与当前缺口见 `18`、`06` §二 |

**`sessionRate` 形状（值与显示分离）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionRate` | `{ tps: number, exact: boolean } \| null` | **只有值**：`tps` 是生成速度，`exact=false` 表示这是下界（缺首字时刻）。`null` = 算不出来（界面显示占位，不编造数值） |

### 2.11 反代账号冷却（失败治理）

| 错误码 | 触发 | 说明 |
|---|---|---|
| `REVERSE_ACCOUNT_SOFT_LIMIT` | 上游 429 | 软限流：600s 起、每次翻倍、封顶 7200s；`error.cooldownUntilMs` 给解冻时刻 |
| `REVERSE_ACCOUNT_BREAKER` | 连续 3 次硬失败（5xx/网络，401/403 不算） | 熔断：1800s 起、封顶 21600s |
| `REVERSE_ACCOUNT_DEGRADED` | 连续 5 次未知失败（其它 4xx/解析失败） | 降权：600s 起、封顶 7200s |

- 冷却状态存 `reverse/<platformId>/<accountId>.state.json`（0600，与凭据文件分开）；冷却期内**不发上游请求**，直接返回上面的错误码。
- 同一账号两次上游请求最小间隔 1s（不足则等待，不报错）。
- 认证类失败（401/403）不冷却账号，走「重新登录」路径。

## 三、数据结构（字段级冻结）

### 3.1 PlatformAccount（群）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 群标识（`groups/:id` 用） |
| `name` | string | 显示名 |
| `avatar` | string? | 头像（URL / 文本占位） |
| `driver` | string | 驱动标识。**写入与读出同名**（`GET /_team/groups` 原样透传配置，无映射层；曾有文档写成读出用 `driverId`，那是未实现的设计意图，以实现为准） |
| `auth.apiKeyRef` | string | 群只保存凭据引用。内置 API 驱动支持 `env:` / `file:`；账号型驱动（如反代）支持 `account:<platformId>/<accountId>`。**按驱动声明的 `authKind` 分流**：`api-key` 走凭据解析，账号型由驱动自己按引用取账号 |
| `summary` | string 或 `{template}` | **读出形状是字符串**（后端按模板渲染后的成品，前端直接显示）；**写入形状是对象** `{ template }`（见 §4.1）。POST 响应回显写入形状、GET 返回读出形状——前端合并时若拿到对象，需用本地渲染串替身，否则界面会出现 `[object Object]`。**模板来源与缺省语义见 §3.9** |
| `lastUpdated` | string\|null | ISO 8601；取值优先级：最近请求行时间 → 群配置时间 → `null` |
| `request` | object? | 请求级覆盖。目前只认 `request.maxTokens`（正整数）：还没学到上限时按它发；一旦某 `(群, 模型)` 从上游 400 学到上限，**学习值会封顶该配置**（发送 `min(配置, 学习值)`）。想重新探测更高上限：删掉 `<dataRoot>/limits.json` 里对应条目（或整文件）。非法值整条计入 `rejected` |

### 3.2 RequestRow（请求记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `time` | string | `HH:mm:ss`（本地时区） |
| `status` | number | `0` = 无上游最终状态（中断）；否则为上游真实状态码 |
| `statusText` | string | 文案（`成功` / `限流` / `客户端中断` …） |
| `model` | string | **改写后**的真实模型（不是虚拟模型名） |
| `account` | `{name,id}` | 必含；群聊视图不单独渲染列，进 `title` |
| `ip` / `ua` | string | 缺失填 `—` |
| `latency` | string | 如 `12.34s` |
| `tokens` | string | `usage.total_tokens`，≥1000 用 `252.6k`；无则 `—` |
| `credit` | string | 上游返回则用，**不估算**；无则 `—` |
| `cacheHit` | string | `cached_tokens / prompt_tokens` 百分比；无则 `—` |
| `requestId` | string | 上游 `id`，无则网关生成 `req-<12位>` |
| `completionTokens` | number\|null | 速率计算唯一合法输入（见 §五.1） |
| `targetSource` | string? | 本次目标的来源：`parent`（继承父会话）/ `last-session`（继承上一会话）/ `fallback-group`（兜底群默认）；**缺省表示显式绑定**（无需提示）。UI 只对这三个值显示提示文案，未知值不渲染并 warn 一次 |
| `latencySeconds` | number\|null | 整步耗时（秒，保留 2 位小数），**含首字等待** |
| `decodeMs` | number\|null | 解码段耗时（毫秒，首个内容分片 → 结束）；速率精确值的分母。`null` = 本次没记到首字时刻（前端只能给下界） |
| `title` | string | 完整原始日志串，**字段顺序固定**（见 §3.2.1 模板），前端直接塞进 `title` 属性 |
| `aborted` | boolean? | 客户端中断时 `true` |
| `claimedReason` | string? | 本次失败由**上游错误认领**判定时写入的机器依据（如 `qoder-code:112`）；未命中认领则不出现该字段（见 §九） |

**出参裁剪**：`startedAtMs` / `firstTokenAtMs` / `usage` 等内部字段**不暴露**；`sessionId` 保留（前端按 session 过滤要用）。`claimedReason` **属于对外字段**，界面要能显示「为什么失败」。

### 3.2.1 `title` 拼接模板（顺序固定）

```
<time> | <status> <statusText> | <model> | <account.name>(<account.id>) | <ip> | <ua> | <latency> | <tokens> | <credit> | 命中 <cacheHit> | <requestId>
```

实例（值用文档保留段，实际为运行时真实值）：

```
03:50:06 | 200 成功 | global:glm-5.3-flash | eightfs(1a1cd1a2) | 192.0.2.10 | deepseek-harness/0.2.0-rc.2 | 14.13s | 252.6k tok | 0.52 credit | 命中 99.9% | req-7e8c519feca47062
```

**为什么顺序必须固定**：这条串是「还原原始日志」的唯一载体（群聊视图不单独渲染 account 列），顺序漂移会让不同 session 的日志无法逐列比对。

### 3.4 DriverMeta

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` | string | |
| `avatar` | string? | |
| `accessMode` | `'official' \| 'reverse'` | 分类信息，不替代驱动声明的认证契约 |
| `authKind` | string? | 由驱动 / 插件声明，当前反代为 `reverse-account`；前端不能据平台名猜字段 |
| `platformId` | string? | 账号型认证所关联的平台，由声明提供 |

`AuthField`：`{ key, label, type: 'text'|'password'|'textarea'|'select', required, placeholder?, options?, showWhen? }`

- `type: 'select'` 必带 `options: [{value,label}]`
- `showWhen: { key, value }`：仅当同表单 `key` 字段值等于 `value` 时才渲染；表单变化后重新求值

### 3.5 FriendGroup（分组）

```jsonc
{
  "id": "g1",
  "name": "强模型组",
  "strategy": "round-robin",       // round-robin | fallback
  "members": [                      // 非空
    { "platformId": "agnes", "modelId": "global:glm-5.3-flash" }
  ]
}
```

- `round-robin`：按游标轮换（游标持久化在 `groups-state.json`）
- `fallback`：始终优先 `members[0]`，失败才顺延（成员有冷却）


### 3.8 TeamMeta（`GET /_team/meta` 响应）

| 字段 | 类型 | 冻结语义 |
|---|---|---|
| `virtualModel` | string | 适配器**实际注册**的虚拟模型名（= `resolveVirtualModelId(config)`） |
| `providerIds` | string[] | 适配器**实际注册**的路由名数组（= `registerAdapter` 的第一个实参） |

- 客户端判定 INV-14 只能用这两个值，**禁止写死**模型名或 provider 名——两者都可由部署方改（`config.virtualModel` / `options.providerIds`）
- 拉取失败按 500ms / 2000ms / 5000ms 三档有限重试（不做定时轮询）；三次仍失败即判「不可知」并隐藏（见下方 INV-14 原文）。端点本身无副作用、无凭证、不读 session

> **INV-14**：悬浮球**仅当**当前会话选中的模型是本插件的虚拟模型时可见。判定依赖两个输入：会话的模型选择、插件元信息是否可用。**任一输入在重试后仍不可用，则判定为「不可知」并隐藏**——宁可少显示，也不把不属于本插件的入口摆给用户。

### 3.9 群列表副标题（`summary`）的声明与透传

群列表里「接入方式 · 地址」那一行由**提供方自己决定显示什么**，通用层只透传。

| 项 | 规定 |
|---|---|
| 声明方 | 插件 / 驱动在自己那侧声明 `summaryTemplate`；平台预置（`config/platforms.json`）里的同名字段也属于该平台的声明 |
| 内容 | **插件想显示什么就写什么**（可以是「账号接入 · {地址}」「限速 60/min · 余额 $12.3」「Token 剩余 2.5M」等任意文案） |
| 通用层职责 | **原样透传**：不解析占位符、不替换变量、不追加入口前缀、不提供任何写死文案 |
| 前端职责 | 直接渲染后端给出的 `summary` 字符串，不认识其中任何内容 |
| 群级覆盖 | 群配置显式写入 `summary.template` 时以群配置为准（用户覆盖优先） |
| 缺省 | 声明缺失 → `summary` 为空字符串，前端**不显示副标题**（不再用「官方接入」或「—」兜底） |
| 变量 | 若文案里需要动态值（地址、余额、限速…），由**声明方自己拼好**再交出来；通用层不提供变量表，也不定义占位符语法 |

> 反面做法（已废弃）：通用层内置默认模板 `官方接入 · {baseURL}` 并用统一替换逻辑渲染——那会让「显示什么」变成通用层的决定，新平台无法表达自己的状态（如余额、并发）。

### 4.5 `POST /_team/import` —— 合并语义

- 默认**合并 upsert**（按 `id`）：已存在更新（计入 `updated`），不存在新增（计入 `imported`）；**绝不整体替换**
- `{"mode":"replace"}` 需先返回 **409**，带 `{"confirm":true}` 才执行
- 群内联的明文 `apiKey` 仍计入 `rejected`；凭证本体只从顶层 `credentialFiles`（相对 dataRoot 的路径 → 内容）还原，写入权限 0600、同名文件先备份 `.bak-<时间戳>`
- 响应：`{ imported, updated, rejected: [{ index, reason }] }`

### 4.6 `POST /_team/models/probe` —— 凭据按驱动 `authKind` 分流

- **只有 `authKind === 'api-key'` 的驱动才解析 API Key 引用**（`env:` / `file:`）；其它认证形态（如账号型 `reverse-account`）**不解引用、不要求** `apiKey` / `apiKeyRef`，`apiKeyRef` 原样传给驱动，由驱动自己取账号。
- `authKind` 缺失按 `api-key` 处理（兼容存量外挂驱动）；内置 `openai-compatible` 已显式声明 `authKind: 'api-key'`，不再依赖"缺省"承担语义。
- 模型清单以驱动 `fetchModels` 的返回值为准，服务端只做既有归一（`normalizeModelList`），不额外拼装；返回空数组就是空数组（不伪造模型）。
- 账号型驱动返回的是**驱动自拉的实时清单**（如 Qoder 运行时请求上游模型目录，10 分钟 TTL 缓存）；拉取失败必须抛错（带明确错误码/状态），**不许返回空数组或静态兜底清单**——探测界面要显示真实原因。
- 失败归一：api-key 驱动的 401/403 仍是 `probe-unauthorized`；非 api-key 驱动归为 `probe-failed`，文案不得出现「API Key」（该平台根本没有这个概念）。

## 五、口径细则

### 5.1 速率（生成速度，不是吞吐）

```
精确值 = completionTokens / (decodeMs / 1000)   // 解码段：首个内容分片 → 结束，不含首字等待
下界   = completionTokens / latencySeconds      // 整步耗时：含首字等待，只在拿不到首字时刻时用
```

**为什么不能只有一个分母**：`latencySeconds` 从请求开始算起，把首字等待（TTFT）也摊进了分母。
长思考模型 TTFT 常占整步的一半以上，用它当唯一分母，速率会被系统性低估；
而 `decodeMs` 只算"已经开始吐字之后"的耗时，才是真实的生成速度。
反过来，`decodeMs` 依赖上游真的吐过分片——非流式兜底、上游直接报错、客户端中断都可能没有首字时刻，
这时只能退回整步耗时，但它是**下界**，必须标出来，不能让下界冒充精确值。

- 单行（`ui/js/format/rate.js`）：`decodeMs > 0` 且 `completionTokens > 0` → `{ tps, exact: true }`；
  否则 `latencySeconds > 0` → `{ tps, exact: false }`；两者都不可用 → `null`
- 会话级：`sum(completionTokens) / sum(分母)`，**不是逐行速率的平均**——平均会让几个 token 的短回复
  和长回复同权。两个桶分别累加，有精确行时精确桶优先；一条精确行都没有才退化成整步桶
- **禁止**用 `tokens / latency` 算：长上下文下输入占绝对多数，会差 100 倍量级。
  真机反例：`tokens=40.3k, latency=4.56s, completionTokens=9` → 正确约 2 tok/s，错算成 8837 tok/s。
- 展示：`<100` 保留 1 位小数；`>=100` 取整；`>=1000` 用 `k`；下界前面加 `≈` 并用 title 说明
  「含首字等待」；无有效数据 `— tok/s`

### 5.2 聊天流排序与按群隔离

- 合并 `rows` 与 `events` 后按 `at`（缺失用 `time`）升序；同键 rows 在前、events 在后
- `?groupId=` 过滤：`/_team/stats/session/:id` 与 `/_team/session/:id/events` 都支持
- 悬浮窗的「本 session 速率 / 全局请求量」**不**按群过滤

### 5.3 环形截断

`stats/requests.jsonl` 超过 `config.stats.maxRows`（缺省 5000）时截断保留最近一半，打 info 日志。

### 5.4 容量相关配置项（T24）

| 字段 | 类型 | 缺省 | 语义 |
|---|---|---|---|
| `contextWindow` | number? | 未设置 | **显式申报值，优先级最高**。想直接指定窗口（比如上游不报容量时手填真实值）就写这个。非法值（`0`/负数/`NaN`/非数字）视为未设置，warning 一次后继续走下一级 |
| `contextWindowFallback` | number | `1048576` | 前两级都拿不到时的申报值（1M）。**必须是正数**——`0`/负数/`NaN` 会让 dsh 抛 `INVALID_MODEL_CONTEXT`，整轮对话起不来 |
| `contextGuard.enabled` | boolean | `true` | 是否在 `stream` 发请求前做超限检查（按「上次成功请求 `prompt_tokens` + 本次新增估算」判断，明确超了才报错，错误里带实际数字） |

**申报取值优先级（三级，逐级回退）**：`config.contextWindow` → 所有已知模型 `contextLength` 的**最小值** → `config.contextWindowFallback`（`1048576`）。

**申报值不只是元数据**：它同时是宿主压缩门禁的基数——本机装的是 `dsh-live-compact`，反应式触发点 = `0.8 × 申报窗口`。申报值虚高会把「该压的时刻」一起推后；它与逐轮切片上限（650k）之间会形成一段无人压缩的带，取舍见 `10` §五。

| 消息映射·工具 | 助手消息里的 `tool-call` 内容块（`{type,id,name,arguments}`，`arguments` 是**原始 JSON 字符串**）必须映射为上游 `tool_calls[]`，正文里**不得**再出现该块的占位文本；`role:'tool'` 消息必须带 `tool_call_id`（取 `message.toolCallId`）。**禁止只保留 `role`+`content`**——那会把调用声明与配对 id 一起丢掉，上游直接 `tool_call_mismatch`（真机必现，见 `06` G-16）。另四条同源硬约束（参考 `dsh-providers-hub` 的 `src/openai-compat.ts` / `src/sse.ts`）：①**孤儿两个方向都要剔**——没有对应调用的工具结果、`name` 为空的调用，上游都回 400；②`tool` 消息必须**紧跟**其 assistant 的 `tool_calls`，中间不得插入 system/developer 消息；③工具结果正文为空时给占位（`(no output)`），不能给空串；④有 `tool_calls` 且无正文时 `content` 必须是 `null`，纯文本消息 `content` 必须保持**字符串**（包装成 `[{type:'text'}]` 会被 400 拒收） |
| 消息映射·role | dsh 的 `developer` 角色与中途 `system` 消息不得原样透传：OpenAI 兼容接口只认 `system`/`user`/`assistant`/`tool`，`developer` 必须映射为 `system` |
| 消息映射·工具图像 | `role:'tool'` 的 `content` **必须是字符串**（OpenAI 兼容接口不接受工具消息带图）。工具结果里的 `image` 块一律**外置**成一条紧跟其后的 `role:'user'` 消息（`[{type:'text'},…{type:'image_url'}]`），并满足三条：① 附图消息只在该**批** tool 结果全部发完之后插入（插在中间破坏 tool 配对，上游 400）；② tool 正文末尾追加「（附图见下一条消息）」，让模型知道图在后一条；③ 一条图都取不到时**不生成**附图消息（空 content 会被拒收），改在 tool 正文里写明「（附图未取到）」。④ **同批多图合并成一条**附图消息，顺序 = tool 结果消息顺序 → 各消息内 image 块顺序。⑤ **跨批各自独立**：每个 assistant 批的结果发完就插它自己的附图消息，不同批不合并。⑥ 占位**两套口径，故意不统一**：用户可见消息用「[图片无法发送：<原因>]」（用户需要知道图坏了、坏在哪），tool 正文用「（附图未取到）」（模型只需要知道有没有，不需要读长句）；部分取到时 tool 正文写「（附图见下一条消息：N 张中 M 张可用）」，**真的全送到才用**不带张数的简版。工具结果里的 `reasoning` 等其它块同样静默丢弃，不得进正文。|
| 消息映射·块类型 | `reasoning` 块**不得**转成正文：要么静默丢弃，要么映射为与 `content` **互斥**的 `reasoning_content` 字段。占位文本（`[<type> 内容已省略]`）**只允许**用在 `image` / `file` 这类「需要让模型知道这里有东西」的块上，其余块静默丢弃——占位文本进入上下文后会被模型当成正文复制，污染对话（真机现象，见 `06` G-18） |
| 依赖 | 不静态 import 宿主包；三级加载：`options.llmModule` → env `DSH_MODEL_TEAM_LLM_SPECIFIER` → `import('@deepseek-ai/dsh-llm')`；全失败则打 error 并**不注册**，不拖垮宿主 |
| 入口 | **禁止 `export default`**（INV-10）；只保留 `export const name` / `export const inject` / `export async function apply` |

### 6.1 转发模式（forward / rewrite，见 `15`）

| 项 | 规定 |
|---|---|
| forward 形态 | 本插件**直接实例化官方 `PiAiAdapter`（`@deepseek-ai/dsh-llm-pi-ai`）**：profile 由群配置解析（端点 = 群 `baseURL`）、凭据由 `resolveApiKey` 返回群自己的。协议转换（消息 / 图片 / 工具 / usage / SSE）由官方库负责。**不经过 `ctx.llm.stream`** |

## 九、上游错误认领（动态加载单文件）

**目的**：上游常把错误写在业务帧里（HTTP 仍是 200）。直接当普通分片透传，就会变成「界面显示已完成、其实一个字都没有」的假成功。
识别这件事**不能写进通用层**（等于把平台判断堆进通用层），改为：**通用层只提供登记与询问，认领规则由各驱动/插件在自己的单文件里声明，注册器按声明里的字符串路径动态加载。**

### 9.1 三层职责

| 层 | 职责 | 禁止 |
|---|---|---|
| 通用层（`src/gateway/drivers/stream-error-claimers.js`） | `registerStreamErrorClaimer({ id, claim })`（返回注销函数）、`claimStreamError(payload, context)`（按注册顺序询问，首个非 null 生效）、测试用 `resetStreamErrorClaimersForTest()` | 认识任何路径、平台名或错误码表 |
| 插件/域注册器（如 `src/reverse/register.js`、驱动注册流程） | 读声明里的**字符串路径** → `await import(new URL(path, import.meta.url))` → 取导出 `claimers` 数组 → 逐个登记；dispose 时逐个注销 | 静态 import 平台实现；把认领函数内联进驱动对象 |
| 平台/驱动**单文件** | 一个文件只做认领：`export const claimers = [{ id, claim }]` | 混入推理、登录等其它职责 |

### 9.2 声明形状

```js
// 平台描述或驱动描述里，只写路径字符串，不 import
streamErrorClaimersModule: './claimers.js',
```

### 9.3 认领返回值（统一契约）

```js
{ code: 'UPSTREAM_QUOTA_EXHAUSTED',              // 稳定枚举，可扩展
  message: '额度/权益不足：<上游原文前 120 字>',   // 给用户看的人话
  reason: 'qoder-code:112',                      // 机器依据，落进请求行 claimedReason
  status: 402 }                                   // 建议映射的状态码，缺省 502
```

- `claim` 返回 `null` = 不认这一帧，继续问下一位。
- **禁止误判**：只带 `usage` 的尾帧（有 `usage`、无 `choices`、无 `code`）不是错误。
- 命中后：按 `status` 记请求行（失败）、`reason` 写 `claimedReason`，`message` 原样抛给上层（上层不得自己重拼文案）。

### 9.4 加载失败必须降级

文件缺失、导出不是数组、单个认领者形状不对 → **warn 一次并跳过该认领者**；推理主流程与其它认领者照常。认领是增强，不是前置依赖。

### 9.5 官方平台同样走这条路

`openai-compatible` 驱动也用同一形状（同目录 `claimers.js` + 同样的动态加载），识别 `{ error: { message, type, code } }` 帧 → `code: 'UPSTREAM_ERROR_FRAME'`、`reason: 'openai-error:<type>'`。**不得存在「只有反代才认领」的特殊路径。**

### 9.6 验收

1. 未登记任何认领者 → 行为与原实现逐字节一致
2. 只加文件 + 声明一行即可接入新平台（不改通用层、不改注册器）
3. 注销后不再命中；重复 `id` 登记即抛错
4. 通用层文件里 `grep -iE "qoder|openai|\.js"` = 0 命中
5. 命中后请求行记失败且 `claimedReason` 可查（不出现假成功）
