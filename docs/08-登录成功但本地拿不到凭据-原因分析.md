# 08 「浏览器显示登录成功，但插件没拿到凭据」原因分析

> 现象：2026-11-08 03:19 的截图中，授权页显示“登录成功”，加群页仍无账号并显示“授权已超时”。
> **该故障根因尚未证实**：截图不能证明操作过慢、没有签发 token，或完成了另一会话的授权。
> 2026-11-08 核对：基线 `c2f6418`；当前账号接口已返回 `origin:login` 的条目，这不能反向证明截图那次故障已修复。活动缺口统一见 `13` R-07。

## 一、先定位现象出现在哪一层

界面文案只有两个来源：

| 文案 | 来源 | 触发条件 |
|---|---|---|
| `授权页已关闭` | `ui/js/interaction/reverse-login.js:104` | `windowRef.closed === true` |
| `授权已超时，请重新登录` | 同文件 `:106-108`（本地判断）、`:123`（收到 expired） | 只说明代码进入对应提示分支，不足以确认故障原因 |

截图只证明界面显示了这句话，不能反推触发分支、实际 elapsed time 或 token 发放状态。须以同一次操作的服务端与前端事件关联为证据，不把文案当作根因。

## 二、把可能的链路逐段对照（含行号）

| 段 | 我们的实现 | 参考实现 | 判定 |
|---|---|---|---|
| 授权 URL | 按 profile 生成（`oauth.js:71-87`） | 两套配置的具体参数见 `09` | 页面成功提示只证明页面给了提示，不证明本地正确领取了同次 token |
| 轮询 URL | nonce/verifier/S256（`oauth.js:91-97`） | 对照函数采用同形参数 | 仍须证实与本次授权操作关联 |
| pending 判定 | 当前 404 / 202（`oauth.js:175-182`） | 参考实现处理有差异 | 只是分类逻辑，不是本次上游返回值的证据 |
| 等待期限 | UI 与服务端各有本地期限 | 期限不同不等于故障根因 | 不调 TTL 修故障，先核对真实事件链 |
| 会话复用证据 | 当前有同平台 pending 复用与平台级 status 查询 | 被引用的 `jet-hub-rpc.js:5727-5777` 实际是 **AStudio 本地会话导入**，不是 Qoder 浏览器登录态检测 | 不能用 `reused` 公共 UI 分支证明 Qoder 已登录就不签发 token |

## 三、证据边界：不能把截图推断写成根因

| 已有证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 授权页显示成功 | 页面给出了成功提示 | 哪个 challenge 被授权、token 是否已领取、是否已落盘 |
| 加群页显示“授权已超时” | 某个界面分支输出了这句话 | 操作实际超时，或故障根因就是等待预算 |
| 两套 client_id / redirect_uri 参数不同 | 源码采用不同客户端配置 | 任一套必错，或改一个参数就修复故障 |
| UI 有重复点击及停止轮询代码 | 存在需要检查的生命周期路径 | 当次故障发生过二次点击、完成了旧授权页 |

没有同一次操作的上游响应、会话关联和落盘记录，不得给这些猜测排序，更不能据此调 TTL、换 profile 或宣布修复。

## 四、要补的可观测性（下一版必做，否则永远在猜）

1. **poll 每次记录一行 debug**：`{ at, status, hasToken, bodyKeys }`（**不含任何 token 值**）
2. `GET /_team/reverse/login/:sessionId` 的返回体增加 `{ pollCount, lastStatus, lastPolledAt }`（枚举与计数，不含凭据），让界面能显示「已轮询 N 次，最后一次状态 404」
3. **不调 TTL 修故障**：等待期限触发只能说明进入了失败分支，不能证明上游未发 token 或用户操作过慢。
4. 超时文案按真实原因区分：
   - 从未收到非 pending 响应 → 「设备授权未完成（服务端一直未发放 token）」
   - 收到 200 但无 token → 「服务端返回了空 token」
   - 服务端 expired → 「授权已过期」

## 五、一次性导入是独立使用路径

- 源解析 → 插件存储出口 → 对外脱敏；导入标记不可续期，不接管他方凭据。
- 当前来源可用，不等于真实导入与真实推理已验收，见 `13` R-05/R-06。
- 浏览器已有登录态不证明宿主持有同一份凭据，也不证明本次授权未发 token。
- **不添加“登录旁边的导入”界面，不把导入优先当作登录故障修法**；前端继续改造暂缓。

## 六、验证顺序（本轮只维护文档）

1. 先打通 `13` R-03/R-04 的群账号引用与流输出接缝。
2. 使用已授权的一次性导入路径验证真实推理，不要求再次登录来试参数。
3. 登录原故障仅按 §四的脱敏关联证据定位；没有证据不调 TTL、不重启碰运气。
4. 前端继续改造暂缓；本轮不下发、不改代码。

## 七、当前会话代码的核对（不是现场根因结论）

当前已有平台级轮询与 pending 会话复用，但仍须验证操作关联及注销路径。

| 环节 | 当前代码 | 可确认的范围 |
|---|---|---|
| 发起登录 | `src/reverse/routes/login.js:65-105` | 已查找同平台 pending 会话再决定新建；代码存在不证明截图那次用了哪条分支 |
| 等待中再次点击 | `ui/js/interaction/reverse-login.js:137-142` | 重开同一 URL；没有再次调用 start 的通常路径 |
| 结果分类 | 同文件 `:87-129` | 已区分 HTTP 错误与 expired；仍有本地等待上限，不能把它当故障原因 |

### 操作关联必须实证

同一次登录至少关联 start、上游 poll、解析、落盘和账号查询；只记录脱敏操作标记、状态和字段名，不记录 verifier、token 或完整授权 URL。

没有这些证据，不能断言发生过二次点击、授权了旧页面或遗失了成功结果。

### 当前仍需验证的风险

- `src/reverse/routes/login.js:156-159` 会优先返回任一历史 `savedAccount`，须验证不会把旧成功当成本次授权成功。
- 取消路由调用 manager，但没有同步外层 `session.state`，须验证取消后不再被复用。
- 上述是源码风险，不是该次截图故障的已证实原因；验证计划见 `13` R-07。

## 八、结果关联与复用的验收要求

1. 平台级查询必须返回**本次操作**的结果，不能只因平台存在历史成功账号就结束新的授权。
2. 会话复用须隔离平台、数据根和调用者；取消、失败、过期后不再复用。
3. 单次授权的领取与落盘须幂等；并发查询不能重复消费一次性凭据或写入重复账号。
4. 这些是应补的行为验收，不能以“代码已经加了平台级查询”声称截图故障已解决。

## 九、错误提示与根因分开

当前 UI 已有 HTTP 错误 / expired 分离逻辑（`reverse-login.js:87-129`）。错误文案只说明分类，不能证明故障原因。不得把网络失败、会话失效或未知回执改写成“授权未完成”，也不得据此调预算。
