# 05 工程执行约定

> 本文件回答"怎么干活"：契约纪律、代码风格、交付前自查、成员调度。
> 契约是什么见 `02`，界面是什么见 `03`。

## 一、契约纪律（R1–R6）

### R1 契约留白 → 先反馈，禁止猜

任何接口/字段/行为在 `02-契约.md`、`03-UI规范.md` 里**没写清**的：

1. 前后端**先反馈**给 Lead（写进对应文档的"待冻结"小节）
2. Lead 组织冻结（写进契约、给出正反例）
3. **冻结后**才实现；冻结前谁都不许"按惯例先做一版"

**禁止**：
- 前端按出参字段名猜写入字段名
- 后端为兼容前端错误写法而放宽校验（`driver || driverId` 这种"兼容"必须由契约决定，不能由实现决定）
- Lead 越过契约直接改一侧代码去"适配"另一侧

> 真实事故：建群接口前端发 `driverId`、后端读 `driver`，加群恒 400；Lead 曾让后端"两种都接受"——那是用放宽校验掩盖违约。

### R2 修 bug 前先判定：代码违例 还是 契约缺失

| 判定 | 处置 |
|---|---|
| 契约写了，代码没遵守 | **改代码**（并补一条门禁用例） |
| 契约没写 / 写得含糊 | **改契约**（冻结），再改代码 |
| 契约与代码都"合理"但不一致 | 同上，以契约为唯一裁决点 |

**禁止**为了让报错消失而放宽校验、加别名、加兜底——那是把违约变成默认。

### R3 写入与读出字段名不同时，必须写死在一处

- 写入侧用配置字段名（例：`driver`），读出侧用接口字段名（例：`driverId`）
- 契约里两处**都要写明**，并各给一个请求/响应样例（见 `02` §4.1）
- 门禁：至少一条用例覆盖"按契约写入 → 能建成功"，用**契约字段名**构造载荷

### R4 同一事实两处表达 → 必须机器门禁（防漂移三条铁律）

1. **真源唯一**：文档只是投影，真契约在代码/注册表；副本必须能证明与真源一致
2. **门禁自证**：新门禁先拿已知 bug 跑一次，**必须变红**；不红 = 摆设
3. **例外数据驱动**：不手工登记例外表（会腐烂）

### R5 文档里的数字与状态必须可核对

- 每个数字（行数/端点数/用例数）都要能回答"什么时候、用什么命令核的"
- 状态性描述（"已完成""待实现"）必须带核对日期
- 修完的条目要迁走（进"已知限制"或 skill），不要长期维护混合表

### R6 收到批评的处理（不辩解）

1. 立即承认，不找借口、不"但是"
2. 分析根因（方向错/理解错/方法错/没验证）
3. 固化进对应文档/契约
4. 当面复述"错在哪、教训是什么、以后怎么做"
5. 需要还原的立即还原

**禁止**机械复读用户原话（"用户说…""用户要求…"）——用自己的话一句话概括后直接给结论/动作。

## 二、代码风格（从第一个文件就执行）

| 规则 | 具体要求 |
|---|---|
| 变量名可读优先 | 禁止 `e/m/g/d/f/v/res/$/esc`；用 `element/event/match/group/driver/field/value/result/escapeHtml` |
| 魔数提常量 | 超时、动画延时、拖拽阈值、边距、行数上限都要有名字（如 `TOAST_DURATION_MS = 2000`） |
| 注释 | 文件头 3~6 行讲职责与关键约定；函数上方一行讲做什么；**总量 ≤ 代码 1/4** |
| 开源清洁 | 不写具体机器环境（路径/用户名/IP/挂载实现）；要表达兼容性就写"兼容受限挂载环境" |
| 单文件上限 | ≤ 400 **代码行**。这是报警线不是硬指标：超了先看是不是把两件事塞进一个文件（是 → 按职责拆，这才是真压缩）；职责本来就单一就**照实超**，交付说明写明「职责单一，X 行，未压缩」 |
| 行数口径 | 只算代码行：空行、纯注释行（`//`、`/* */`、JSDoc 的 `*`）**不计入**。度量：`node scripts/code-lines.mjs <files>` |

**可读性 > 行数（违反即视为不通过）**：禁止为了压行数做下列任何一件——删注释、删空行、把多行挤成一行（`a(); b(); c();`）、用嵌套三元代替 if/else、把职责不同的逻辑硬合并、缩短成 `d/v/tmp` 这类要翻上下文才懂的命名。压到目标行数需要上述任一手法时，**放弃压缩、照实写**，并在交付说明里写清「职责单一，X 行，未压缩」。

## 三、交付前自检清单（固定 6 条，缺一条不算完成）

| # | 检查项 | 为什么有这条 |
|---|---|---|
| 1 | **真机端到端**：在目标实例上按用户路径走一遍，覆盖「新增/切换/刷新/重进」 | 历史：9 个前端 bug 里 6 个是真机才发现，本地 mock 全部"通过" |
| 2 | **契约字段核对**：每个写入载荷对照后端校验器逐字段核（字段名/嵌套位置/可选必填） | 历史：`driverId` vs `driver` 导致加群恒 400 |
| 3 | **刷新往返一致**：涉及持久化就比对"改完立刻看到"与"刷新后读到" | 历史：系统消息双源，刷新后文案不一致 |
| 4 | **生命周期路径**：挂载/卸载类改动覆盖首挂、重复挂载、卸载后再挂 | 历史：二次挂载后新 DOM 无监听，面板空白 |
| 5 | **渲染副作用**：自动 focus / scroll / 定时器，重渲染后要复验 | 历史：每次渲染无条件 focus 搜索框 |
| 6 | **门禁全绿**：`check-contract` + `build.cjs` + `--check lib/client.js` + `test/*.test.js` + 代码行口径 | 防止"只测改的那一点" |

## 四、任务收尾五步（固定动作，不许跳）

1. 跑一遍静态审计，真实命中顺手修，误报说明理由
2. 跑全套验收脚本（`04` §五对应阶段那一块）
3. 停服务、清残留（端口释放、进程 0、临时夹具不留）
4. **同步到安装副本**：`sync_plugin pluginName=dsh-model-team`（先 dryRun 看会写哪些文件，再 `write:true`），并核对安装副本 `lib/client.js` 与工作区 **md5 一致**。不同步 = 用户在界面上看到的还是旧版，而本地一切验收都是绿的（踩过：加群界面还停留在阶段 1 的旧表单与 Mock 文案，工作区里早就删了）
5. **更新进度文档**：`08` 阶段 G 对应行勾掉并补提交 sha；缺陷已修的从 `06` §二 删除、把教训写进 §三。**验收通过 ≠ 收尾完成**，文档没同步等于下一轮又从旧状态开始
6. 带实测证据汇报（不接受"应该没问题"）

## 五、验收纪律

- **独立验收**：验收方自己复跑，不采信实现方自报全绿
- **前端必须实际渲染**：真实渲染截图/无头浏览器，`node --check` + `curl API` 不算完成
- **反例自证**：新门禁先演示"打破 → 变红 → 还原 → 全绿"
- **一手证据**：汇报里贴命令与输出，不贴结论
- **UI 视觉由用户最终确认**：界面观感、文案、布局以用户判断为准；AI 不得自评「好看」「符合预期」，只能给出实际渲染截图供判断（历史：界面细节由用户逐条确认后才定稿）
- **UI 验收用现成工具，不自建服务端**：`minihost`（把插件服务端代码跑起来，模拟宿主、改码刷新即生效）+ `preview`（生成单文件 HTML、跑真实 `client.js` 与垫片，`--backend` 指向 minihost 端口）两步串起来就是「真实 client + 真实后端」。**禁止**为联调临时搭静态壳或手写 mock 传输层——那正是「本地通过、真机失败」的来源
- **用 minihost 验收必须显式传 `env`**：minihost 只隔离 `DSH_HOME`，**不隔离**本插件的数据根变量 `DSH_MODEL_TEAM_HOME`。不传就会读写真实数据根（实测：minihost 起的实例直接读到了真实 config 里的 2 个群）。验收命令固定写成
  `minihost start plugin=<本仓库> env={"DSH_MODEL_TEAM_HOME":"<临时目录>"}`，跑完删临时目录

## 六、成员调度（一次一个）

| 规则 | 说明 |
|---|---|
| 一次只让一个成员改仓库 | 并发下发会让两人同时动同一批文件，中途打断留半成品（真实事故：改名任务同时派前端与后端，前端被打断后 `preview/`、`lib/` 处于半改名状态） |
| 串行顺序 | 先定契约（Lead）→ 派一个成员改 → 验收/提交 → 再派下一个 |
| 下发写清**独占范围** | 例：后端只改 `src/`、`test/`、`package.json`、`cordis.patch.yml`；`ui/`、`lib/`、`docs/` 归别人 |
| 不追着催进度 | 消息会自己到达，等待期间做自己那份不冲突的工作 |
| **成员出问题立刻停手，交用户处理** | 判定信号：收到消息后**没动任何文件**就失败、连续两次同一位置失败、留下半成品但有提交缺失。满足任一条就**停止一切下发**，把现象（几次、什么表现、仓库是否干净）报给用户，由用户决定换人/换会话/自己处理。**不许连试三次**（真实事故：m0-contract 旧会话连续三次空转失败，第三次才停，浪费三轮） |

## 七、版本号（以本节为准）

- **版本号由用户决定**：AI **不得自行升级**（不自动 +1、不猜 minor/patch）
- AI 的职责：把本次变更整理进 README 版本记录**候选条目**，交付说明里列「建议版本号 + 理由」，等用户给号
- 用户给号后，才同步三处（`package.json`、README 版本记录、必要的代码内常量）
- 纯文档 / 纯清理改动的版本归属同样由用户决定

> ⚠️ 本节取代旧文档里"里程碑完成升 minor / 修复升 patch"的自动升版规则。两套规则并存是旧文档的缺陷之一，本套只保留这一份。

## 八、挂载环境兼容纪律

本项目要能跑在受限文件系统上（CIFS/SMB：无 exec、无软链接、无 chmod）：

- 脚本不依赖可执行位：一律 `bash x.sh` / `node x.mjs` 显式解释器调用
- 项目内**不使用软链接**；依赖装在项目内并由 `.gitignore` 忽略
- 安装依赖时兼容无 bin 链接的环境（`.npmrc`：`bin-links=false`、`ignore-scripts=true`）
- 产物不依赖 chmod/mode 位
- 项目 PID 文件写在项目根 `<项目全称>.pid`；启停走自带脚本（start/stop/restart/status）
