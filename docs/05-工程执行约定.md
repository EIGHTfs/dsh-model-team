# 05 工程执行约定

> 本文件回答"怎么干活"：契约纪律、代码风格、交付前自查、成员调度。
> 契约是什么见 `02`，界面是什么见 `03`。

## 一、契约纪律（R1–R8）

### R1 契约留白 → 先反馈，禁止猜

任何接口/字段/行为在 `02-契约.md`、`03-UI规范.md` 里**没写清**的：

1. 前后端**先反馈**给 Lead（写进对应文档的"待冻结"小节）
2. Lead 组织冻结（写进契约、给出正反例）
3. **冻结后**才实现；冻结前谁都不许"按惯例先做一版"

**禁止**：
- 前端按出参字段名猜写入字段名
- 后端为兼容前端错误写法而放宽校验（`driver || driverId` 这种"兼容"必须由契约决定，不能由实现决定）
- Lead 越过契约直接改一侧代码去"适配"另一侧

> 真实事故：建群接口前端发 `driverId`、后端读 `driver`，加群恒 400；Lead 曾让后端"两种都接受"——那是用放宽校验掩盖违约。

### R2 修 bug 前先判定：代码违例 还是 契约缺失

| 判定 | 处置 |
|---|---|
| 契约写了，代码没遵守 | **改代码**（并补一条门禁用例） |
| 契约没写 / 写得含糊 | **改契约**（冻结），再改代码 |
| 契约与代码都"合理"但不一致 | 同上，以契约为唯一裁决点 |

**禁止**为了让报错消失而放宽校验、加别名、加兜底——那是把违约变成默认。

### R3 写入与读出字段名不同时，必须写死在一处

- 写入侧用配置字段名（例：`driver`），读出侧用接口字段名（例：`driverId`）
- 契约里两处**都要写明**，并各给一个请求/响应样例（见 `02` §4.1）
- 门禁：至少一条用例覆盖"按契约写入 → 能建成功"，用**契约字段名**构造载荷

### R4 同一事实两处表达 → 必须机器门禁（防漂移三条铁律）

1. **真源唯一**：文档只是投影，真契约在代码/注册表；副本必须能证明与真源一致
2. **门禁自证**：新门禁先拿已知 bug 跑一次，**必须变红**；不红 = 摆设
3. **例外数据驱动**：不手工登记例外表（会腐烂）

### R5 文档里的数字与状态必须可核对

- 每个数字（行数/端点数/用例数）都要能回答"什么时候、用什么命令核的"
- 状态性描述（"已完成""待实现"）必须带核对日期
- 修完的条目要迁走（进"已知限制"或 skill），不要长期维护混合表

### R6 修改与提交必须在确认范围内

- 文档修改先确认目标和范围；**用 `edit` 小段修改，禁止脚本、重定向或整篇覆盖代替编辑**。
- 按“读一个段落 → 修改该段落 → 核对结果”推进；锚点不匹配就重读当前段落，不扩大替换范围。
- 修改授权不自动包含提交、推送、升版、部署或重启授权；未确认这些动作时只落盘供检查。
- 清理旧文档时直接纠正过期结论，不追加互相矛盾的补充结论；未经实证不得写“根因已定位”。

### R7 全项目低耦合的派发与验收

- 每次派发都写清：声明方、发现方、注册方、公开接口、禁止依赖、故障隔离和注销路径。不能只写“低耦合”三个字。
- 反代插件声明自己的路由，model-team **动态发现、动态注册**；通用流程不得静态依赖具体插件实现。详细契约见 `18`。
- 验收必须覆盖插件缺失、动态加入、停用、再启用及单插件失败，不能只验证已有插件能被 import。
- 全部功能均执行同一边界规则；目录搬迁、单测全绿不等于用户主路径或插件化验收完成。

### R8 收到批评的处理（不辩解）

1. 立即承认，不找借口、不"但是"
2. 分析根因（方向错/理解错/方法错/没验证）
3. 固化进对应文档/契约
4. 当面复述"错在哪、教训是什么、以后怎么做"
5. 需要还原的立即还原

**禁止**机械复读用户原话（"用户说…""用户要求…"）——用自己的话一句话概括后直接给结论/动作。

## 二、代码风格（从第一个文件就执行）

| 规则 | 具体要求 |
|---|---|
| 变量名可读优先 | 禁止 `e/m/g/d/f/v/res/$/esc`；用 `element/event/match/group/driver/field/value/result/escapeHtml` |
| 魔数提常量 | 超时、动画延时、拖拽阈值、边距、行数上限都要有名字（如 `TOAST_DURATION_MS = 2000`） |
| 注释 | 文件头 3~6 行讲职责与关键约定；函数上方一行讲做什么；**总量 ≤ 代码 1/4** |
| 开源清洁 | 不写具体机器环境（路径/用户名/IP/挂载实现）；要表达兼容性就写"兼容受限挂载环境" |
| 单文件上限 | ≤ 400 **代码行**。这是报警线不是硬指标：超了先看是不是把两件事塞进一个文件（是 → 按职责拆，这才是真压缩）；职责本来就单一就**照实超**，交付说明写明「职责单一，X 行，未压缩」 |
| 行数口径 | 只算代码行：空行、纯注释行（`//`、`/* */`、JSDoc 的 `*`）**不计入**。度量：`node scripts/code-lines.mjs <files>` |

**可读性 > 行数（违反即视为不通过）**：禁止为了压行数做下列任何一件——删注释、删空行、把多行挤成一行（`a(); b(); c();`）、用嵌套三元代替 if/else、把职责不同的逻辑硬合并、缩短成 `d/v/tmp` 这类要翻上下文才懂的命名。压到目标行数需要上述任一手法时，**放弃压缩、照实写**，并在交付说明里写清「职责单一，X 行，未压缩」。

| 7 | **同步部署副本**：改了 `src/**` 或 `lib/client.js` 就同步 profile，然后跑 `node scripts/check-deploy-parity.mjs` 直到一致 | 真实事故：修复已入库但线上跑旧文件，表现为静默丢数据（`06` G-24） |

## 三点五、测试不稳定时禁止调预算（2026-11-05 立，硬规则）

**断言失败 → 先查设计，不许改等待时长。** 连续多次「这次红了、重跑就绿」时，正确动作是让测试**不依赖时间**，而不是把 8s 改成 20s、再改成 40s。

| 症状 | 错误做法 | 正确做法 |
|---|---|---|
| 等某个 UI 状态超时 | 把 `timeoutMs` 调大 | 让被测方**先给出确定的完成信号**（如 `window.__DMT_BOOT__`、store 状态位），测试只等信号；信号不到的根因通常是"失败后不重试"而不是"慢" |
| 点击没命中 | 循环点 3 次 | 等布局稳定（几何连续两帧不变）再点一次；命中不了是真 bug（球的坐标/hit-test 有问题） |
| 页面加载慢到一个场景 50s | 每个场景加预算 | 一个场景一次整页导航本身就该审视：能否复用页面、能否缩小夹具 |
| 偶发 1/7 失败 | 加重试开关 | 记录失败率与证据；**允许重试的唯一形式是"等信号"**，不是"重跑断言" |

**判据**：一次测试的等待预算必须是**同一个常量**（如 `SCENARIO_TIMEOUT_MS`），任何场景单独写出不同的数字即视为违规，评审时直接打回。

**为什么立这条**：真实事故——同一份代码 3 天里被反复调预算 4 次（8s→10s→20s→30s），每次都"看起来好了"，但根因（客户端首次加载失败后永不重试）一直在，且**真实用户也会碰到空列表**。调预算把这个产品缺陷藏进了测试配置里。

**补充决定（同日）**：浏览器端自动化测试**整体移除**，不再保留任何形态。理由是它在本机的耗时是 3.4s～50s（浏览器冷启 + 后端每请求 fork），且每一次"红了"都被当成等待问题而不是设计问题。替代原则：

1. **能静态判定的，就静态判定**：层级顺序、层名引用、无魔数、显隐规则、遮罩铺满——全部对源码做断言（`scripts/check-css.mjs`），几十毫秒、零抖动。
2. **能在数据层判定的，就在数据层判定**：渲染输出、字段文案、计数一致性——`scripts/check-render.mjs` 在 vm 里跑真渲染函数。
3. **只有"真的要看一眼"的，才人工看**：颜色、间距、动效手感。人看一次的成本低于维护一条不稳定的管道。

判据：新增一条断言前先问「这条不启浏览器能不能判」。能判却写成浏览器断言，评审直接打回。

## 四、任务收尾五步（固定动作，不许跳）

1. 跑一遍静态审计，真实命中顺手修，误报说明理由
2. 跑全套验收脚本（`04` §五对应阶段那一块）
3. 停服务、清残留（端口释放、进程 0、临时夹具不留）
4. **同步到安装副本**：`sync_plugin pluginName=dsh-model-team`（先 dryRun 看会写哪些文件，再 `write:true`），并核对安装副本 `lib/client.js` 与工作区 **md5 一致**。不同步 = 用户在界面上看到的还是旧版，而本地一切验收都是绿的（踩过：加群界面还停留在阶段 1 的旧表单与 Mock 文案，工作区里早就删了）
5. **更新进度文档**：`08` 阶段 G 对应行勾掉并补提交 sha；缺陷已修的从 `06` §二 删除、把教训写进 §三。**验收通过 ≠ 收尾完成**，文档没同步等于下一轮又从旧状态开始
6. 带实测证据汇报（不接受"应该没问题"）

## 五、验收纪律

- **独立验收**：验收方自己复跑，不采信实现方自报全绿
- **前端必须实际渲染**：真实渲染截图/无头浏览器，`node --check` + `curl API` 不算完成
- **反例自证**：新门禁先演示"打破 → 变红 → 还原 → 全绿"
- **一手证据**：汇报里贴命令与输出，不贴结论
- **UI 视觉由用户最终确认**：界面观感、文案、布局以用户判断为准；AI 不得自评「好看」「符合预期」，只能给出实际渲染截图供判断（历史：界面细节由用户逐条确认后才定稿）
- **UI 验收用现成工具，不自建服务端**：`minihost`（把插件服务端代码跑起来，模拟宿主、改码刷新即生效）+ `preview`（生成单文件 HTML、跑真实 `client.js` 与垫片，`--backend` 指向 minihost 端口）两步串起来就是「真实 client + 真实后端」。**禁止**为联调临时搭静态壳或手写 mock 传输层——那正是「本地通过、真机失败」的来源
- **用 minihost 验收必须显式传 `env`**：数据根三档优先级是 `DSH_MODEL_TEAM_HOME` → `DSH_HOME/dsh-model-team` → `HOME/.dsh-model-team`。minihost 只隔离 `DSH_HOME`（0.2.5 起这已经能隔出独立数据根），但它**不会**隔离显式覆盖变量 `DSH_MODEL_TEAM_HOME`——若沿用真实数据根，要先确认没把它指向正式目录。验收命令固定写成
  `minihost start plugin=<本仓库> env={"DSH_MODEL_TEAM_HOME":"<临时目录>"}`，跑完删临时目录

## 六、成员调度（一次一个）

| 规则 | 说明 |
|---|---|
| 一次只让一个成员改仓库 | 并发下发会让两人同时动同一批文件，中途打断留半成品（真实事故：改名任务同时派前端与后端，前端被打断后 `preview/`、`lib/` 处于半改名状态） |
| 串行顺序 | 先定契约（Lead）→ 派一个成员改 → 验收/提交 → 再派下一个 |
| 下发写清**独占范围** | 例：后端只改 `src/`、`test/`、`package.json`、`cordis.patch.yml`；`ui/`、`lib/`、`docs/` 归别人 |
| 不追着催进度 | 消息会自己到达，等待期间做自己那份不冲突的工作 |
| **成员出问题立刻停手，交用户处理** | 判定信号：收到消息后**没动任何文件**就失败、连续两次同一位置失败、留下半成品但有提交缺失。满足任一条就**停止一切下发**，把现象（几次、什么表现、仓库是否干净）报给用户，由用户决定换人/换会话/自己处理。**不许连试三次**（真实事故：m0-contract 旧会话连续三次空转失败，第三次才停，浪费三轮） |

## 七、版本号（以本节为准）

- **版本号由用户决定**：AI **不得自行升级**（不自动 +1、不猜 minor/patch）
- AI 的职责：把本次变更整理进 README 版本记录**候选条目**，交付说明里列「建议版本号 + 理由」，等用户给号
- 用户给号后，才同步三处（`package.json`、README 版本记录、必要的代码内常量）
- 纯文档 / 纯清理改动的版本归属同样由用户决定

> ⚠️ 本节取代旧文档里"里程碑完成升 minor / 修复升 patch"的自动升版规则。两套规则并存是旧文档的缺陷之一，本套只保留这一份。

## 八、挂载环境兼容纪律

本项目要能跑在受限文件系统上（CIFS/SMB：无 exec、无软链接、无 chmod）：

- 脚本不依赖可执行位：一律 `bash x.sh` / `node x.mjs` 显式解释器调用
- 项目内**不使用软链接**；依赖装在项目内并由 `.gitignore` 忽略
- 安装依赖时兼容无 bin 链接的环境（`.npmrc`：`bin-links=false`、`ignore-scripts=true`）
- 产物不依赖 chmod/mode 位
- 项目 PID 文件写在项目根 `<项目全称>.pid`；启停走自带脚本（start/stop/restart/status）

## 测试抖动：单跑复绿 + 留痕

- 全量红时**先单跑失败文件**（`node --test <file>`），不许直接怀疑被测代码。
- 单跑绿 = 抖动，**可以放行，但必须留痕**：`node scripts/test-all.mjs` 会自动写 `artifacts/flaky.jsonl`（时间、失败文件、失败断言前 40 行）。
- **禁止**用「多跑几次总会有一次绿」代替诊断；这类绿灯不算验证通过。
- 抖动记录累计 ≥3 条时单独立项，用日志自证法（在关键点打时间戳/计数）定位，不要当场猜着改用例。
- 门禁的 `test` 道与本地全量都走 `node scripts/test-all.mjs`；必须严格全量时用 `--no-retry`。
- 门禁会把抖动告警透出到输出（`✓ test` 下一行的 `⚠ 抖动：…`），所以"通过但抖动"在门禁日志里同样看得见；留痕文件只保留最近 200 条。
- 同步（sync_plugin / 手工复制）后再跑一次 `check-deploy-parity`：既要逐字节一致，也**不该有副本多出的残留**（旧布局的 `.js`/`.json` 会被宿主真的加载，属失败项）。

### 验收必须走「用户实际入口」

- **接口通过 ≠ 功能可用**：任何面向用户的功能，验收时必须从**用户真正会走的那条路**进一次（点击/输入/命令），而不是只跑单测、curl 接口。
- 反面教材：反代登录只做了 CLI 与内部状态机，加群页面上**没有登录入口**，提交直接报「缺少 API Key」——服务端全绿，功能等于不存在。
- 检查清单（交付前逐条问）：
  1. 用户在哪儿看到这个功能？截一张图
  2. 从那个位置点下去，能不能走完主路径？（不是"接口能通"）
  3. 失败时用户看到的是什么？文案里有没有让他去敲命令行
  4. 界面里出现的名字是否就是用户该看到的（别带内部术语，如「反代」）
- UI 验收用 `minihost` + `preview` 渲染真实 client.js，**不要**为此另起服务端。

### 0.3.0 保留版本（不许提前用）

- **0.3.0 是一个里程碑版本，不是"下一个补丁"**：只有「Qoder 作为第一个反代平台**真实接入成功**并通过验收」时才允许升到 0.3.0。
- 在此之前的一切改动（迁移、UI、修复、其它平台）**一律停在 0.2.x**，按现状递增；不存在"先升 0.3.0 再补验收"的做法。

  1. 用真实账号在 DSH 里**发一条消息并收到完整回复**（流式结束、无报错）
  2. 请求行写入正确（模型名、状态码、latency、usage）
  3. 界面路径可达：从「加群」页面点一次就能登录并自动选中账号（不许出现命令行提示、不许点两次）
  4. 失败语义正确：401/未登录/加密不可用三种情况都是**明确错误**，且没有降级到公开端点
  5. 日志与接口回执中搜不到 token 明文
