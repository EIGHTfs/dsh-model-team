> 这张表只做一件事：**把「文档怎么写的」「代码怎么做的」「线上跑的是哪份」三列并排**，任何一列对不上就是缺陷。

## 一、为什么会需要这张表

同一件事在三处各写一遍，必然漂移。本项目真实发生过：

| 事故 | 漂移形态 |
|---|---|
| 工具图片丢失（G-24） | 契约没写「工具结果的 image 块去哪」→ 实现自己决定 → 修复做了但**没同步部署副本** → 线上还是旧行为 |
| 群列表空白（G-16） | 契约写 `driver`，实现读 `driverId`，文档没写清哪个是读写名 |
| 悬浮球常显（G-23） | 契约写「只在选中虚拟模型时显示」，实现里有两个「判不了」分支一个常显一个常隐 |
| 门禁假绿（G-11c） | 文档说「环境变量可覆盖」，实现里覆盖失败会静默回落 |

**结论**：不是「文档不准」或「代码不听话」，而是**同一个事实没有单一真相源，也没有机器门禁**。

## 三、A-15 的处置（唯一系统性缺口）

**问题**：改完代码 → 跑门禁全绿 → 忘记 `sync_plugin` → 线上还是旧行为。2026-11-05 的「虚拟模型看不到图」就是这么来的，而且**表现是静默丢数据**，不是报错。

**修法（按可靠性排序）**：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 机器核对 | 门禁加一条：把仓库 `src/**`、`lib/client.js` 与 profile 副本逐文件比 md5，不一致就失败 | **推荐**。但只在「本机有部署副本」时成立，换机器/CI 会误报，需 `--allow-no-deploy` 兜底 |
| ② 提交前自动同步 | 提交脚本里带 `sync_plugin` | 会把副作用塞进只该读的流程，否决 |
| ③ 改成软链 | profile 副本软链到工作区 | 违反「项目目录禁止软链」；且 realpath 变化会击穿宿主模块缓存 |
| ④ 靠人记 | 现状 | 已被证明不可靠 |

**当前选择**：先做 ①（`scripts/check-deploy-parity.mjs`，作为可选第七道门禁，默认运行、`--allow-no-deploy` 可跳过），并把「改完代码必须同步部署副本」写进 `12` 收尾步骤。

## 四、维护规则

1. 新增契约条目 → 本表加一行，三列都填；缺哪列就填「无」，不许留空。
2. 改实现 → 检查本表同行，三列是否仍然一致。
3. **状态列出现 ⚠️/❌ 时，必须在本文件记下缺陷编号**（`13` 的 G-xx），否则视为漏记。
4. 本表由 `check-deploy-parity.mjs` 覆盖 A-15 一列；其余靠评审，不靠脚本（脚本判不了语义）。
