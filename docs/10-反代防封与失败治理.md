# 10 反代防封与失败治理

> 一句话：**同一账号在服务端看来必须始终是「同一台设备」；失败时不硬打，按族退避。**
> 本文是防封与失败治理的唯一权威（数值、状态文件、错误码语义）。平台差异只写在各平台目录内。
> 核对：2026-11-08，基线 `bd6c689`。

## 一、为什么需要

厂商风控按「设备身份 + 请求节奏 + 失败模式」画像。三个典型封禁诱因，本插件都必须避开：

| 诱因 | 表现 | 后果 |
|---|---|---|
| 设备指纹漂移 | 同一账号两次登录拿到不同的 `machineToken` / `machineType` | 被当成「多设备共用账号」 |
| 请求过密 | 同一账号连续请求间隔远小于官方客户端 | 触发限流乃至风控 |
| 失败硬打 | 429 / 5xx 之后立刻重试 | 放大风险信号，且把账号打死更快 |

## 二、设备指纹（由账号身份派生）

`src/reverse/platforms/qoder/fingerprint.js`：

| 字段 | 派生方式 | 稳定性 |
|---|---|---|
| `machineToken` | `userId + salt` → sha512 → base64url，取 43 字符 | 同一 uid **恒定** |
| `machineType` | `userId + salt` → md5 → 18 位 hex | 同一 uid **恒定** |

**合并规则（`mergeFingerprint`）**：已有值优先，只补空缺。

- 为什么这么定：存量账号里已经落过随机 `machineToken`，若直接覆盖，等于让这个账号「换了设备」，反而制造漂移。
- 因此第一次升级时老账号保持原值；新账号从一开始就是派生值。
- 派生算法写在平台目录内（`platforms/qoder/`），`core/` 不出现任何平台名。

## 三、失败治理（账号级三族）

状态文件：`<dataRoot>/reverse/<platformId>/<accountId>.state.json`（0600、原子写、与凭据文件分开）。

| 族 | 触发 | 首次窗口 | 放大方式 | 封顶 | 错误码 |
|---|---|---|---|---|---|
| 软限流 | 上游 429 | 600s | 每次翻倍 | 7200s | `REVERSE_ACCOUNT_SOFT_LIMIT` |
| 熔断 | 连续 3 次硬失败（5xx / 网络） | 1800s | 每次翻倍 | 21600s | `REVERSE_ACCOUNT_BREAKER` |
| 降权 | 连续 5 次未知失败（其它 4xx / 解析失败） | 600s | 每次翻倍 | 7200s | `REVERSE_ACCOUNT_DEGRADED` |

统一退避式：`base * 2^(n - offset)`，封顶、最多放大 20 步。数值与参考实现同源（`_refs/qoder2api-hub/qoder_accounts.py:1319-1330`）。

**语义约定**：

- 冷却期内**不发上游请求**，直接返回上表错误码，并带 `cooldownUntilMs`（解冻时刻）。
- **401/403 不冷却**：那是「凭据失效」，正确处置是重新登录，不是等。
- 任一次成功即复位该账号的计数与窗口。

## 四、请求间隔

同一账号两次上游请求最小间隔 **1s**（常量，非魔数），不足则**等待**而不是报错。

- 参考实现同口径（`qoder_accounts.py:1096`，注释明确「≥1.0s 防风控」）。
- 等待用注入的 `now` / `sleep` 实现，测试里不真等。

## 五、UA 与设备头

| 项 | 取值 | 说明 |
|---|---|---|
| 推理 UA | `undici` | 与 Python 参考默认一致（`qoder_sign.py:528`），可用 `DSH_MODEL_TEAM_QODER_UA` 覆盖 |
| `cosy-machineid` / `cosy-machinetoken` / `cosy-machinetype` | 来自账号凭据 | 三者必须**成套**，缺一即失败 |

不要擅自把 UA 改成带插件名的字样（如 `dsh-model-team/...`）——那是最容易被识别为脚本的指纹。

## 六、未验证项（不许当成已完成）

| 项 | 现状 | 验证方式 |
|---|---|---|
| 429 / 5xx 真实行为 | 用例是注入桩，**未打真实上游** | 真机上故意撞一次限流（或用尽额度的小号），看是否进冷却并能在窗口后恢复 |
| 派生 `machineToken` 是否被 CN 侧接受 | **未验证** | 用派生指纹的账号完成一次真实对话，并观察后续请求是否被拒 |
| 虚拟机环境风险画像 | 参考实现会读官方 `runtime-info` 的 `vmInfo`，我们**没做** | 若出现「账号可登录但请求被限」，先查是否虚拟机画像 |

## 七、怎么验（可复跑）

## 八、边界

- 本文只覆盖**账号自身的节流与退避**，不做代理池、不做多账号轮换调度（那是 M4 账号池的范围，尚未实现）。
- 不做任何绕过风控的手段：只让请求「像官方客户端那样正常」，不伪造官方进程、不改服务端判定。

## 九、上游错误认领（已修：业务错误被当成成功空回复）

**问题**：上游有「HTTP 200 + 单帧错误体」的回法（实测 Qoder `code=112`，message 里是定价页链接）。这类帧没有 `choices`，被当成无关帧跳过；HTTP 状态仍是 200，于是请求行记成功、界面显示「已完成」，用户却一个字都没收到。**假成功比报错更糟：排查时看不出任何异常。**

**修法**：通用层只提供两个动作——登记认领者、逐帧询问（`src/gateway/drivers/stream-error-claimers.js`，里面没有任何平台名/错误码表/文件路径）。认领规则写在各自的单文件里（`export const claimers = [{ id, claim }]`），由注册器按声明里的字符串路径 `await import(new URL(path, import.meta.url))` 动态加载：

| 位置 | 声明 |
|---|---|
| 反代平台（`platforms/<平台>/index.js`） | `streamErrorClaimersModule: './claimers.js'` + `streamErrorClaimersBase: import.meta.url` |
| 官方驱动（`drivers/<驱动>.js`） | 同上两行；认领文件与驱动同目录 |
| 通用层 | 只 `registerStreamErrorClaimer` / `claimStreamError` / `resetStreamErrorClaimersForTest` |

命中后按认领给的 `status` 记请求行（失败），`reason` 落进 `claimedReason` 字段（对外可见，界面能显示「为什么失败」），`message` 原样抛给上层。**加载失败/导出非法/单个认领者形状不对 → warn 一次并跳过**，推理主流程照常（认领是增强，不是前置依赖）。

**怎么加一个新平台**（三步，不改通用层、不改注册器代码）：
1. 在平台目录新建单文件（只做认领），导出 `claimers = [{ id: '唯一标识', claim(payload) { ... return null | { code, message, reason, status } } }]`；
2. 平台描述里加一行 `streamErrorClaimersModule: './claimers.js'`（字符串路径，不 import 平台文件）；
3. 跑 `node --test test/stream-error-claimers.test.js` 与全量用例——认领者的注册名是 `<driverId>#<id>`，重复即抛错。

**已知边界**：认领只能发现「上游主动告诉我们的错误帧」；上游若返回 200 + 空流（连错误帧都没有），仍需靠账号健康度与日志定位，这条不在本机制覆盖范围内。
