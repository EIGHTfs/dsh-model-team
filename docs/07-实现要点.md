# 07 实现要点（踩坑换来的，代码里读不出来）

> 本文件只装一类知识：**从代码看不出来、但不知道就会做错的机制与坑**。
> 契约是什么见 `02`，界面长什么样见 `03`。本文不重复它们。

## 一、session ID 怎么拿（唯一正确做法）

### 1.1 结论

把**零渲染组件**注册进 `conversation.input.dock` 槽位，读 `props.session.sessionId`（`props.sessionId` 也可）。

### 1.2 四条被实测否定的路（别再试）

| 路线 | 为什么不行 |
|---|---|
| URL 路由 | DSH 是 SPA，路由里没有 session id；刷新后丢失 |
| 客户端全局对象 | 宿主不暴露，挂 `window` 上也是各插件各写一份，拿不到当前 session |
| 服务端 SSE / 事件推送 | 只有"最近活跃"的推断，**不等于用户正在看的那一个**（见 1.3） |
| 轮询 `/_team/sessions/current` | 同上 + 有延迟，切换 session 不能秒感知 |
| `shell.overlay` 槽位 | **最容易踩**：看起来"最像浮层"，但拿不到任何 session 信息 |

### 1.3 宿主当前 session ≠ 服务端 `sessions/current`（实测）

真机同一时刻：

```
宿主 UI 当前 session（槽位给出）      : <session-id-宿主侧>…
服务端 GET /_team/sessions/current : <session-id-服务端>…
```

服务端接口是"最近活跃"的**推断**。⇒ **session id 只能以槽位为准**；服务端接口仅适合"没有前端上下文"的场景（CLI、外部调用）。

### 1.4 事实依据（宿主 0.2.1-alpha.2 实测）

```
client/ui-conversation/lib/client.js:21141
  renderSlot("conversation.input.dock", zone)      // zone = { session, input }

session 对象字段：session.sessionId
标题来源：useSessions(state => state.byId[id].title)
```

真机探针读出的 props 键：`usePanelInfo, useSessions, useSessionStatus, useWorkspaces,
useResource, useSessionRetainInfo, sessionId, inputActions, useSession, useConversation,
useInput, useTrajectory`；组件会被反复重渲染（每次 session/输入态变化），**不要在里面做重活**。

## 二、session 目标回落（4 级，带 `targetSource`）

| 顺序 | 条件 | 采用 | `targetSource` |
|---|---|---|---|
| 1 | 本 session 有映射 | 本 session target | `explicit` |
| 2 | 无映射但有父 session，且**父链上任一祖先**有映射 | 最近命中的祖先 target（**递归向上**） | `parent` |
| 3 | 都没有，但存在其它已绑定 session | 其中 `updatedAt` 最新者的 target（排除本 session） | `last-session` |
| 4 | 以上都没有 | `session.fallbackGroupId` 的 `defaultModel` | `fallback-group` |
| — | 连兜底群都没配 | 报错 `model-unresolved` | — |

**dsh 侧事实依据（两处独立证据）**：

1. **类型定义** `packages/core/agent/lib/types/index.d.ts:64-71`：agent meta 声明 `parentSession` / `origin: "subagent"` / `delegationDepth`
2. **生产日志实测**（2026-11-03）：真实子代理日志 `sessions/<工作区>/<父-session-id>…/subagents/<子-session-id>…/session.v4.jsonl.zstd` 解压后首行 header 的顶层键为 `type, version, id, createdAt, cwd, parentSession, isSeeded, delegationDepth, agentPreset`，其中 `parentSession = <父-session-id>…`（正是父 session 的 id）

⇒ **`parentSession` 在 header 顶层**（不在 meta 内），与本插件 `session-fallback.js:24` 读 `hostSession.header.parentSession` 一致；同时兼容 `header.parentSessionId`。

**三条关键点**：
- 父链是**递归向上**的（子 → 父 → 祖父），取**最先命中**的，不是只看直接父
- 「上一个 session」以**映射文件的 `updatedAt`** 为序，不用宿主活跃时间（映射更新才代表"绑过模型"）
- 推断结果**不写回**本 session 映射（避免把推断冒充成用户显式选择），只在请求行记 `targetSource`

## 二点五、当前 session 选中了哪个模型（INV-14 的实现前提）

**事实**：模型选择**不在** session header 里（header 顶层只有 type/version/id/createdAt/cwd/parentSession/isSeeded/delegationDepth/agentPreset），而在运行时 projection 中：

```js
// packages/client/ui-conversation/lib/client.js:19081-19089
const model = session.projections.faceOf("modelSelection").getSnapshot();
const selection = model?.next ?? model?.lastUsed;   // → { provider, model, reasoningEffort }
```

**含义**：服务端无法判断「当前 session 是否选中虚拟模型」，只能由客户端读。

**实现路径已确认（2026-11-03 查 dsh 类型定义）**：

session 作用域的槽位（含 `conversation.input.dock`）由宿主注入三件标准 props（`packages/client/ui-session/lib/types/client/index.d.ts:77-84`）：

```ts
interface SessionStandardProps {
  useSession: SessionSnapshotSelector;   // 当前 session 生命周期与控制状态
  sessionId: SessionId;                  // 当前 session 身份
  useProjection: UseProjection;          // 按 projection key 取值
}
```

`UseProjection` 的签名（`packages/api/session-controller/lib/types/client/sessions/projection-store.d.ts:28-31`）：

```ts
<K extends keyof SessionProjectionMap>(key: K): SessionProjectionMap[K] | undefined;
<K, S>(key: K, selector: (value) => S, eq?): S;   // 带 selector 的重载，引用稳定
```

所以 INV-14 的判定逻辑：

```js
// meta = GET /_team/meta 的结果（契约 02 §3.8）：{ virtualModel, providerIds }
// 组件 props 里直接有 useProjection（session 作用域自动注入）
const selection = props.useProjection("modelSelection");
const current = selection?.next ?? selection?.lastUsed;
const usingOurs = current !== undefined && meta !== null
  && meta.providerIds.includes(current.provider)
  && current.model === meta.virtualModel;
if (!usingOurs) return null;               // 不渲染悬浮球
```

**注意**：

1. `useProjection` 返回 `undefined` 表示「该 projection 尚无值」（宿主未挂载或首帧未到），此时按**不显示**处理，不要抛错
2. `provider` 是本插件注册的路由名（`ctx.llm.registerAdapter(providerIds, ...)` 的第一个实参），与 `config.virtualModel`（模型名）是两个字段，比较时要分开
3. `ui-model-selection` 插件负责该 projection 的投影逻辑（`packages/client/ui-model-selection/lib/client.js:981`），若它未启用则拿不到值
4. 两个比对值**只能来自 `/_team/meta`**，客户端不许写死常量——部署方可以改 `config.virtualModel` 与 `options.providerIds`，写死会让球在该显示的部署上永远不显示（`test/inv14-model-gate.test.js` 只守得住缺省值，守不住自定义）
5. meta 还没到就判 → 结论是 `unknown`（先不显示）；meta 到达后要**重算一次**，所以判定要收敛成一个纯函数 `decideDock({ selection, meta, projectionAvailable })`，桥与 meta 加载器都只调它（这样 7 态可以纯函数测）。`projectionAvailable === false` 表示宿主没有 `useProjection`，必须单独判成 `degraded`——否则会被「selection 无值 → unknown」吃掉，退化成球永不显示

## 二点六、上下文容量（contextWindow）怎么申报给 dsh

**dsh 的取值链路**（`packages/compaction/compaction-basic/lib/index.js:743-749` 与 `:936-940`）：

```js
function routedTarget(session) {
  const config = session.requestHeader()?.config;   // 上次请求头里 dsh 记录的 config
  return { provider: config.provider, model: config.model };
}
// …
const info = await this.ctx.llm.resolveModelInfo(target.provider, target.model, signal);
if (info.context === void 0) throw new TargetPressureConfigError(...);   // 没申报 → 直接抛错
const spec = resolveCompactSpec(policy, info.context.contextWindow, ...);
```

**唯一的申报通道**：adapter 的 `resolveModel` 返回 `LlmResolvedModelInfo`，其中 `context?: { contextWindow }`。
`listModels` 返回的 `LlmModelInfo` **没有** contextWindow 字段（那个只用于列表展示）。

**为什么本项目无法精确申报**（三条硬约束，都有代码依据）：

1. `resolveModelInfo(provider, model, signal)` 与 `prepareCall(provider, model, signal)` 的入参**都没有 sessionId** —— 申报时不知道当前 session 指向哪个真实模型
2. `ConfigureCall` 类型注释明写「**The returned controls cannot change the captured route**」—— adapter 不能把 `config.model` 改写成真实模型
3. 因此 `session.requestHeader().config.model` 永远是虚拟模型名 → 压缩永远按虚拟模型的申报值算

**参考实现（dsh-providers-hub）为什么能精确**：它把每个真实模型注册成独立路由（`src/accio-product.ts` 40+ 条，每条带 `contextWindow`），一个模型一个窗口。本项目的「一个虚拟模型 + 运行时改写」在架构上做不到同样的事。

它的三条踩坑注释值得照抄：

- 未知模型**不编造**窗口（宁可让 DSH 用默认值，也不报一个假窗口）
- `0` / 负数 / `NaN` 会让 DSH 抛 `INVALID_MODEL_CONTEXT`，**整轮对话起不来**（不是降级，是崩）
- 兜底只给「窗口全来自本地静态表」的家（codearts），不得推广到其他家

**上游能给什么**（2026-11-03 实测 `sa6400.local:7863`，42 个模型）：

| 字段 | 覆盖 | 说明 |
|---|---|---|
| `context_length` | 39/42 | 数字，语义最直接（如 300000 / 1000000） |
| `max_allowed_size` | 39/42 | 数字；2 条与 `context_length` 不一致（如 960000 vs 1000000） |
| `context_window` | 23/42 | **对象** `{ default, supported[] }`，取 `default` |
| `max_output_tokens` | 39/42 | 输出上限 |
| 三个全缺 | 3/42 | 全是**图像模型**（本无上下文概念） |

**归一化优先级**：`context_length` → `max_allowed_size` → `context_window.default` → 不填（UI 显示 `—`，符合 INV-07）。

**申报规则（已定）**：`resolveModel()` 返回的 `context.contextWindow` 取「所有已知模型 `contextLength` 的**最小值**」——
虚拟模型底下可能挂着任意一个真实模型，取最低值才是安全下界。

- 数据源：首次需要时**探测一次**所有群的 `models.endpoint`，结果缓存在进程内存（探测失败不抛错，退兜底）
- 兜底：`config.contextWindowFallback`，缺省 **262144**（262K）。dsh 拿不到 `context` 会直接抛 `TargetPressureConfigError`，所以必须给数
- **per-request 切换声明做不到**：`prepareCall(config)` 没有 session，拿不到该会话的真实目标；`ConfigureCall` 的类型注释写明「返回的 controls 不能改变已捕获的路由」；而压缩读的是 `session.requestHeader()?.config`（= `prepareCall` 返回的 config）。所以请求头里永远是虚拟模型
- 真实模型的窗口只能用在两处：UI 如实展示 + `stream` 里发请求前按「上次成功请求的 `prompt_tokens` + 本次新增消息估算」判超限，**明确超了才报错**（错误信息里带实际数字与窗口，便于判断是不是误报）

## 三、客户端状态工厂（三条硬规则）

### 3.1 R1 单一真相源

- 状态**只有一份**：`createTeamStore()`（`ui/js/store.js`）
- 视图只 `getState()` + 订阅事件；**禁止**自己 `fetch`、**禁止**视图之间互相通知刷新

### 3.2 R2 读回早于首次渲染

- 首屏必须先把持久化数据读回（群列表、当前 target），再渲染
- 否则会出现"先显示空，再跳一下"或"永远空"

### 3.3 R3 apply 与 render 分离

- `apply` 只做"绑定与订阅"，`render` 只做"读状态 → 写 DOM"
- 混在一起会导致：一次状态变化触发多次渲染、渲染里又改状态 → 循环

### 3.4 事件清单（唯一允许的视图刷新触发点）

`target:changed` / `session:changed` / `chat:updated` / `stats:updated` / `groups:updated` / `view:changed`

**除这六个事件外，任何地方都不许主动触发重渲染。**

### 3.5 session 切换必须秒感知（禁止轮询）

- 靠槽位桥（§一）拿到新 sessionId → 触发 `session:changed` → 各视图自行重取
- **禁止**用 `setInterval` 轮询 session（旧实现有 1500ms 轮询，切换 session 有明显延迟）

## 四、拖拽跟手（5 条机制，缺一条就"不跟手"）

| # | 机制 | 做错的后果 |
|---|---|---|
| 1 | 拖动期**只写 `transform`**，绝不写 `left/top` | 每帧触发 layout，肉眼可见卡顿 |
| 2 | `requestAnimationFrame` 合并：同一帧多次 `pointermove` 只写一次 | 高频事件把主线程打满 |
| 3 | 松手必须 `flushDockFrame()`：只 `cancelAnimationFrame` 会丢最后一帧 | 球停在离手几像素的位置 |
| 4 | 尺寸缓存：拖动中**不调** `getBoundingClientRect()` | 每帧强制同步布局，掉帧 |
| 5 | 4px 阈值 + `touch-action: none` | 轻微抖动就误判成拖动；移动端被浏览器滚动抢走手势 |

**验收（可量化）**：
- 拖动中 `pointermove` 次数 : DOM 写入次数 ≥ 2:1（证明有合并）
- 松手后球的最终位置与最后一次 `pointerup` 坐标偏差 ≤ 1px（证明没丢帧）
- 拖过 4px 前不应出现 `is-dragging` 类

## 五、8 条实测坑

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 宿主给三方插件的 `client.js` **不带内容指纹** | 改完必须**硬刷新**，否则跑旧 bundle（曾误判"字段不见了"） |
| 2 | 入口写了 `export default` → `inject` 被宿主 `||` 吃掉 | 只保留命名导出（INV-10） |
| 3 | 在 profile 级 `node_modules` 放假 shim 会毒死宿主 | 用 env `DSH_MODEL_TEAM_LLM_SPECIFIER` 指真实路径 |
| 4 | 二次挂载（HMR / 重复 apply）后新 DOM 无监听 | 检测 `.dmt-host` + `#floatDock` 同时存在就复用 |
| 5 | `.hidden` 用 `display:none` | 用 `visibility/opacity/pointer-events`，否则开合动画失效 |
| 6 | 渲染后无条件 `focus()` | 只在原本聚焦于输入框时恢复 |
| 7 | 多源数据拼接排序 | 先定排序键（`at`，缺失用 `time`）+ 同键规则 |
| 8 | 固定尺寸容器放长文本 | 量 `scrollWidth > clientWidth`，用最长值测 |
