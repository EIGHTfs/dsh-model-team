# 12 协议适配与转发模式设计稿

> 官方协议已有 forward / rewrite 实现，调用边界见 `15`；通用协议插件化与 Qoder 完整接入尚未验收。
> 两种模式都使用群自己的端点与凭据，不另选宿主 provider。私有平台协议由可选插件声明并提供，model-team 动态发现、动态注册；低耦合边界见 `18`。

## 一、两种模式（同一入口，可参数切换）

| 模式 | 做什么 | 谁负责转换 | 适用 |
|---|---|---|---|
| `forward` | 使用群自己的配置与凭据直接实例化官方 `PiAiAdapter`，不再次进入 `ctx.llm.stream` 路由 | 官方适配器 | 已验证的官方协议路径；不是复用其他宿主 provider |
| `rewrite` | 由已登记驱动完成请求 / 流转换；私有平台规则留在可选插件内 | 所选驱动 / 插件 | 不支持官方直调的协议；Qoder 接缝缺口见 `06` |

选择逻辑以 `02` §6.1 与 `15` 为准：合法显式 `mode` 优先，缺省 forward；这只是官方协议的当前分流，不是私有反代协议已经打通。

**forward 的实际前提**：官方包及 `resolveProfiles` 可用、使用群自己的配置与凭据实例化适配器。`GenerateOptions` 无 per-call 端点 / 凭据覆盖；不得借用其他宿主 provider，亦不得为了接口不可用另增群级 provider 字段。

## 二、协议收敛到工厂（加一家 = 加一条注册，不改主链路）

```js
// 每个协议实现一个 ProtocolAdapter（本插件的子模块，见 09 的 kind: 'protocol'）
export const id = 'gemini';
export const capabilities = {
  dshAdapterAvailable: false,     // dsh 有无该协议适配器 → 决定能否 forward
  imageParts: 'inline',           // 'inline' | 'attachment' | 'unsupported'
  reasoningField: 'thought',      // 该协议回传思考用的字段名；null = 不回传
  systemRole: 'system',           // 有的协议叫 systemPrompt / instructions
  toolCallIdField: 'call_id',
  usagePath: 'usageMetadata',     // 上游 usage 的位置
};
export function buildRequest({ messages, tools, target }) { /* → { url, headers, body } */ }
export function parseStreamChunk(rawEvent) { /* → dsh StreamChunk[] */ }
export function extractUsage(payload) { /* → TokenUsage | null */ }
```

通用协议设施只消费插件声明并校验公开接口，不维护另一个平台名单，也不把协议映射到其他宿主 provider。新增或移除实现须动态生效且故障隔离；当前通用插件发现缺口见 `06` R-01。
**好处**：新增一家协议 = 一份文件 + 一条注册；主链路（会话、路由、请求行、错误分类）零改动。

已知协议清单（按是否已有 dsh 适配器分）：

| 协议 | dsh 有适配器 | 我们怎么办 |
|---|---|---|
| openai-completions / openai-responses | ✅（pi-ai） | forward 优先；rewrite 作为对照实现 |
| anthropic-messages | 有（pi-ai anthropic api） | 同上 |
| gemini | ✅（pi-ai googleGenerativeAI） | 同上 |
| accio / astudio / minimax / modelscope / opencode | ❌ | rewrite（照 `dsh-providers-hub` 的 `*-messages.ts` 逐家实现） |

## 三、rewrite 模式的硬约束（都是真机教训，已进 `02` §六）

1. `tool-call` 块走 `tool_calls[]`；`role:'tool'` 必带 `tool_call_id`
2. 孤儿双向剔除（结果无调用、调用 `name` 为空）
3. `tool` 消息必须紧跟 assistant 的 `tool_calls`，中间不得插 system/developer
4. `arguments` 是**原始 JSON 字符串**（解析成对象会让 dsh 估算器得 NaN，会话打不开）
5. `reasoning` 不得转正文；占位文本只给 `image`/`file`
6. 空工具结果给 `(no output)`；有 `tool_calls` 无正文时 `content: null`；纯文本保持字符串

**形状探测**（参考实现的做法）：按消息形状判断是 ≤0.1.6（user 内嵌 `tool-result` 块）还是 0.1.7+（一等 `role:'tool'`），**不认版本号**。两种都要支持，否则 dsh 升级/混用时工具会被整批丢弃。

## 四、forward 模式的硬约束

1. 不再次把请求路由给虚拟 provider，也不要求群配置另一个宿主 provider。
2. 官方适配器使用群自己的端点、凭据和真实模型；能力不可用时按 `02` §6.1 明确记录失败或降级。
3. 真实调用链须验证消息、工具、usage 和完成语义；手工构造的对照 chunk 只能验证形状。
4. 私有反代驱动不能被当成普通 OpenAI 官方调用绕过；这项分流与接缝尚有 `06` 的缺口。

## 五、两种模式怎么验证（可证伪）

| 用例 | 判据 |
|---|---|
| 同一会话同一工具调用，rewrite 模式 | 上游收到 `tool_calls` + `tool_call_id` 配对完整 |
| 同一会话同一工具调用，forward 模式 | 结果语义一致；dsh 侧 usage 与 rewrite 相差 <5% |
| 图片消息 | rewrite：文本占位（能力位 unsupported）；forward：真实 image parts |
| dsh 形状为 legacy `tool-result` | 两种模式都不丢工具（形状探测生效） |
| 人为破坏 forward 前提（provider 未注册） | 自动降级 rewrite 且 warn，请求仍成功 |

## 六、与现有代码的关系

- 现有 `adapter-support.js` 的转换即 `rewrite` 模式的 **openai-completions 协议实现**，不删，收编进工厂
- 现有 `toOpenAiToolCalls` / `toOpenAiMessages` 保持为「openai-completions 协议」的内部实现
- 新增 `forward` 分支只加一处调度，不碰请求行/错误分类/会话映射

## 七、风险

| 风险 | 处置 |
|---|---|
| forward 依赖非公开字段，dsh 升级可能失效 | 启动探测 + 失败降级 + 明确日志 |
| 两种模式行为分叉 | 同一组回放用例跑两遍，差异即失败 |
| 协议条数膨胀 | 每协议一份文件、能力位必填；CI 断言能力位齐全 |
| 递归/自指 | 目标 provider 显式排除自己 |
