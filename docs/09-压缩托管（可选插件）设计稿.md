# 09 压缩托管（可选插件）设计稿

> 状态：**未实现**，仅设计稿。本文件不属于现有 8 份主文档，是给「未来可选增强」留的路标。
> 结论先行：**可以做成独立 DSH 插件，不需要改 `dsh-model-team`**；它是可选增强，没有它时本插件行为完全不变。

## 一、为什么要独立成插件

| 理由 | 说明 |
|---|---|
| `ctx.compaction` 每 context 只允许一个实现 | 谁继承 `CompactionEngine` 并注册谁掌管压缩；挂在路由插件里等于把两件事绑死 |
| 失败面不同 | 压缩插件起不来，宿主应回落到 stock 压缩；而路由插件起不来只影响「选这个虚拟模型」的会话 |
| 可卸载 | 从 `dsh.profile.bundles` 移除即恢复原生行为，不需要动路由插件 |
| 职责单一 | `dsh-model-team` 管「请求落到哪个真实模型」；压缩管「上下文生命周期」 |

## 二、三个角色与边界

| 角色 | 职责 | 谁提供 |
|---|---|---|
| 申报值 | `resolveModel()` 返回 `context.contextWindow`，三级：配置 → 已知最低 → 兜底 | `dsh-model-team`（已有） |
| 会话 → 真实模型 | `GET /_team/session/:id/target` | `dsh-model-team`（已有） |
| 何时压缩 / 压到多少 / 怎么摘要 | 实现 `CompactionEngine` 并注册 `ctx.compaction` | **新插件** |
| 禁用内置压缩 | bundle patch + 结构化 overlay | **新插件** |

关键：压缩插件决策时**能拿到 session**（`CompactionEngine` 的方法是 `(agent, signal)` 形状），因此可以「查该 session 的真实模型 → 查它的窗口 → 自己算阈值」。这正是 `resolveModelInfo` 那条路做不到的事（那条路没有 session，见 `06` §四点五）。

## 三、机制四步

1. **注册引擎**：`class TeamCompaction extends CompactionEngine`，`super(ctx, 'compaction')`；实现 `compactNow(agent, signal, commandId)`（`/compact` 命令会调它）与自动触发（监听 `agent/pre-step`）。
2. **禁用内置**：两层，缺一不可——
   - 宿主层：bundle patch 给 `compaction-basic` 行打 `auto: false`
   - preset 层：web profile 的压缩跑在 agent preset **内层**，patch 按 id 打不到 → 必须结构化扫描「任何把 `dsh-compaction-basic` / `dsh-command-compact` 嵌在 plugins 树里的条目」并禁用
3. **gate 服务 + 回落**：preset 会 `inject` 一个 gate 服务才注册；我们没起来时 gate 不提供，preset 回落 stock。**这条不是可选项**——参考项目原注释：旧接线在这条路径上「把会话创建直接搞砖了」。
4. **决策**：`agent.session.id` → `GET /_team/session/:id/target` → 真实模型 → 窗口（群配置 / 探测缓存）→ 自己算「是否超阈值」。申报值仍由路由插件给（可以给得很大，因为压不压由我们说了算）。

## 四、参考项目学习点（ranxianglei/billion-context）

| 他们的做法 | 为什么 | 我们怎么用 |
|---|---|---|
| `dsh.bundle.patch.yml` 给 `compaction-basic` 打 `auto: false` | 宿主层能按 id 命中 | 照抄 |
| `src/agent/dsh-compaction-disable.ts`：结构化 overlay，扫描 preset 内层 plugins 树 | web profile 的压缩在 preset 内部，按 id 打不到（他们 issue #1772/#2360） | 照抄（这是最容易漏的一层） |
| 独立的 `bili-compaction-gate` 常开条目 | 禁用插件与 gate 必须解耦；kill 掉主插件时 gate 仍在，preset 才能回落 stock（#3662） | 照抄 |
| 明确「必须真禁用，不能共存」 | dsh 的压缩检查点会把原始历史**持久遮住**，两边都压会互相破坏原料 | 照抄，不要试图共存 |
| 每次改写登记到进程级 telemetry | bundle patch 可能命中不存在的 id，漏配只在宿主日志里可见（#3962） | 简化版：启动时打一行「已禁用 N 条」 |

**不照抄的**：他们是完整压缩引擎（外部存储、fold point、多级保留、mysql2 依赖）。我们只做「按真实窗口决定要不要压」，摘要沿用 dsh 现有语义。

## 五、MVP 范围（若要做）

- 只做：按真实模型窗口触发压缩（阈值 = 窗口 × 可配比例）、调用摘要、写标准 `compaction/start` 事件与检查点消息
- 不做：外部存储、多级保留、跨会话共享、自定义摘要 prompt 模板
- 验收：① 选出低于申报值窗口的真实模型 → 到阈值就压 ② 没有本插件时行为与现在完全一致 ③ 本插件崩掉 → 会话仍能创建（回落 stock）

## 六、风险

| 风险 | 处置 |
|---|---|
| 两层禁用漏一层 → 双压互毁 | 启动自检：检测到内置 compaction 仍加载就报错并**主动不接管** |
| gate 没提供 → preset 卡在等待 | 必须实现回落分支；没有把握就保持 stock |
| 我们算错窗口 → 压缩过早/过晚 | 窗口未知时**不压**（交给宿主/上游报错），不猜 |

## 七、没有这个插件时（默认路径）

`dsh-model-team` 按三级优先申报（`config.contextWindow` → 已知模型最低值 → `contextWindowFallback`，缺省 1M），dsh 内置压缩按这个值判断。行为与现在完全一致，**不依赖本设计稿的任何内容**。
