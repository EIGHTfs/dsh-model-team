# 20 「浏览器显示登录成功，但插件没拿到凭据」原因分析

> 现象（2026-11-08 03:19 实测截图）：
> ① 授权页 `qoder.cn/device/selectAccounts?challenge=…` 显示 **登录成功**，账号是 **理论永久最恒久**（既有账号）
> ② 同一时刻插件加群页：账号下拉仍是 **(尚无账号)**，提示 **「授权已超时，请重新登录」**，提交禁用

## 一、先定位现象出现在哪一层

界面文案只有两个来源：

| 文案 | 来源 | 触发条件 |
|---|---|---|
| `授权页已关闭` | `ui/js/interaction/reverse-login.js:95` | `windowRef.closed === true` |
| `授权已超时，请重新登录` | 同文件 `:98`（本地 deadline）或 `:113`（服务端返回 `expired`） | 本地计时到点 / manager 判定过期 |

截图是「授权已超时」，说明**不是**窗口被关（否则会是「授权页已关闭」）。因此走的是 `:98` 或 `:113`，即「轮询期间一直没拿到 token，直到超时」。

## 二、把可能的链路逐段对照（含行号）

| 段 | 我们的实现 | 参考实现 | 判定 |
|---|---|---|---|
| 授权 URL | `src/reverse/platforms/qoder/oauth.js` 按 profile 拼；`cn-python` 带 `redirect_uri=qoder-work-cn://` | `qoder_accounts.py:4458-4462`（CN 必发 redirect_uri） | ✅ 页面能打开且显示「登录成功」，说明 URL 与服务端接受度都没问题 |
| 轮询 URL | `GET {openApiBase}/api/v1/deviceToken/poll?nonce&verifier&challenge_method=S256` | 同（`qoder_accounts.py:4489-4493`、`qoder.js:93-99`） | ✅ 参数一致 |
| pending 判定 | 404 与 202 都算 pending | `qoder_accounts.py:4497-4498`（404/202） | ✅ 已对齐 |
| 超时窗口 | `300s`（`platforms/qoder/index.js` login.timeoutMs） | `QODER_LOGIN_TIMEOUT_MS = 300000`（`qoder.js:…`） | ⚠️ 相同，但用户实际操作可能超过（点登录 → 切浏览器 → 授权 → 回来） |
| **会话复用** | **完全没有处理**：只要浏览器里已有登录态，页面直接「登录成功」，我们继续傻等 token | 参考实现有显式的 `reused` 分支：`jet-hub.js:10161-10165` —— 检测到「已复用本机已有凭据」时**立刻停止轮询**并告知用户，不再拿 URL 去等 | ❌ **最可能的根因** |

## 三、结论（按可能性排序）

### H1（最可能）：授权页复用了浏览器已有登录态，没有为本次 challenge 签发 token
- 证据链：截图里账号是既有账号「理论永久最恒久」；页面文案是「现在，你可以返回 Qoder，开始你的 AI 编码之旅」——这是**已有会话**的完成页，不是设备授权的新 token 发放页。
- 参考实现的对应处置：`jet-hub.js:10161-10165` 的 `res.reused` 分支——服务端判定「已复用已有凭据」时，UI 显示「已复用本机已有的账号凭据，未新建账号」并**不轮询**。
- 我们的缺口：轮询没有任何「设备页已完成但没有 token」的分支，只能等到超时。

### H2：300s 窗口不够
- 我们与参考都是 300s；但参考是桌面端、点完即授权；用户是手机浏览器 + 切标签，实际可能超过。
- 判别方法：看服务端日志里该 session 的 poll 次数与首次/末次时间。

### H3：轮询参数与服务端预期仍有细微差异
- 两家参考都用 `nonce/verifier/challenge_method=S256`，我们一致；但**授权 URL 与轮询 URL 必须属于同一 challenge**（我们复用同一 session 对象，理论上成立）。
- 若 H1、H2 都排除，才需要怀疑这一点。

### H4：本地 deadline 与服务端 expired 的先后
- 我们本地也有 death line（`:98`），可能与服务端同时到点，掩盖真实原因。

## 四、要补的可观测性（下一版必做，否则永远在猜）

1. **poll 每次记录一行 debug**：`{ at, status, hasToken, bodyKeys }`（**不含任何 token 值**）
2. `GET /_team/reverse/login/:sessionId` 的返回体增加 `{ pollCount, lastStatus, lastPolledAt }`（枚举与计数，不含凭据），让界面能显示「已轮询 N 次，最后一次状态 404」
3. `TTL` 提到 **600s**，并在界面显示「剩余时间」（用户知道窗口还剩多久）
4. 超时文案按真实原因区分：
   - 从未收到非 pending 响应 → 「设备授权未完成（服务端一直未发放 token）」
   - 收到 200 但无 token → 「服务端返回了空 token」
   - 服务端 expired → 「授权已过期」

## 五、功能层的真正出路（不只是修文案）

**对「浏览器已经登录过」的用户，登录本来就不是必需路径** —— 直接复用已有账号即可：

- 我们已经建好「凭据导入」框架（`src/reverse/core/import/`，源 `host-credentials` / `manual`），且 `host-credentials` 在重启后即可用；
- 正确产品路径应该是：
  1. 先尝试**导入**（宿主里已有 Qoder 凭据 → 一次点击拿到账号）
  2. 导入拿不到，才走**设备授权**（且必须处理 `reused` 语义）
- 也就是说：**当前实现把「设备授权」当成了唯一入口，这才是设计层面的偏差**；参考实现的 `account.create` 是「先复用、再新建」的顺序（`jet-hub.js:10150-10165`）。

## 六、下一步动作（按顺序）

1. 加可观测性（§四 1-4），重启一次
2. 让用户再点一次「登录」——这次日志会直接说出 poll 到底返回了什么
3. 同时把「导入优先」接进 UI（前端暂缓中，可先只做服务端 API 使用路径）
4. 若日志证明 H1：实现 `reused` 语义（poll 连续 N 次 404 且浏览器侧已完成 → 提示改用导入）

## 七、更正：真正的原因（不是超时）——会话与授权页不一一对应

之前的 H1/H2 都是猜。把两侧代码摆在一起看，问题在**会话生命周期**：

| 端 | 代码位置 | 行为 |
|---|---|---|
| 服务端 | `src/reverse/routes/login.js:59-76` | **每次** `POST /reverse/login/start` 都 `manager.start()` 生成**新 sessionId**，放进 `loginSessions`，**不复用**同平台已有会话 |
| 前端 | `ui/js/interaction/reverse-login.js:126` | 每次点「登录 Qoder」先 **`stopReversePoll()`** —— **杀掉上一次的轮询**；`:132` 再创建一个新会话 |
| 前端 | 同文件 `:103` | 轮询回执若没有 `status` 字段（例如 HTTP 404 错误体），**默认当成 `expired`**，于是界面显示「授权已超时」 |

### 由此产生的必然结果

1. 用户第一次点登录 → 浏览器打开**授权页 A**（session A），前端开始轮询 A
2. 用户等了一会儿觉得没反应 / 或界面提示超时 → **再点一次** → 前端 `stopReversePoll()` **停掉 A 的轮询**，并创建 **session B**、打开**授权页 B**
3. 用户实际在**授权页 A** 上完成了授权（浏览器显示「登录成功」，账号正是既有账号「理论永久最恒久」）
4. 前端只轮询 B —— A 的授权结果**再也没有人去取**，B 的页面用户没碰
5. 300s 到点 → 界面「授权已超时」

也就是说：**授权是成功的，只是成功的那次会话被我们自己丢弃了**。这与「超时」在因果上无关——超时只是最后的表现。

### 为什么之前没发现

- 服务端 `loginSessions` 是进程内 Map，按 sessionId 索引，**没有「按平台查最近会话」的能力**；
- 前端把上一次轮询停掉时**没有任何日志**；
- 轮询错误体（404）被 UI 的 `:103` 兜底成 `expired`，把「会话不存在/错误」伪装成「超时」。

## 八、正确做法（三条，缺一不可）

1. **轮询按平台、不按会话**
   `GET /_team/reverse/login/status?platform=<id>` → 扫描该平台所有活跃会话，任一 `granted` 即返回该账号；这样**任何一次授权都不会被丢弃**，也不会因为点了两次而错位。
2. **同一平台复用进行中的会话**
   `POST /reverse/login/start` 若该平台已有 `pending` 且未过期的会话 → 返回**同一个** `sessionId` 与 `loginUrl`（带 `reused: true`），不再新建。
3. **UI 不再"点一次就杀上一次"**
   等待中再点，应当：① 重新聚焦/重新打开**同一个** `loginUrl`；② 不 `stopReversePoll()`；③ 只有 `expired/cancelled` 后才允许新建。

## 九、顺带要修的第三个真问题

`ui/js/interaction/reverse-login.js:103` 把「回执没有 status」当 `expired`。正确做法：把 HTTP 错误与「授权过期」分开显示——
- 404（会话不存在）→「登录会话已失效，请重新登录」
- 5xx/网络 →「登录服务异常（HTTP xxx）」
- 只有服务端明确返回 `expired` 才显示超时
