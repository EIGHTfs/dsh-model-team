## 二、B10 任务详情（消息排序门禁）

### 背景（代码分析结论，非猜测）

`ui/js/view/messages.js` 的 `messageSortValue` 把时间**砍成「当天毫秒偏移」**：

```js
return when.getHours() * 3600000 + when.getMinutes() * 60000 + when.getSeconds() * 1000;
```

跨日即失效：昨天 `23:50` → 85800000，今天 `00:11` → 660000，于是「新消息」被判成比旧消息更早。
数据里其实**有绝对时间**：请求行 `startedAtMs`（epoch 毫秒）、会话事件 `at`（带日期的 ISO），但都没被当排序键。

用户观察到「有的组倒序、有的正常、有的不更新」，与「仅跨日才乱」吻合。

**决定**：本轮**不修排序**，只加门禁——先把现状钉死并可定位，修的时候有回归保护。

### 交付物（三道门禁）

| 编号 | 形态 | 内容 | 判据 |
|---|---|---|---|
| G1 | 单测，进 `test/` | `buildMessages` 的排序契约：同日内升序、**跨午夜**（23:50 昨天 vs 00:11 今天）、绝对时间优先（同时有 `time` 与 `startedAtMs`/`at`）、同秒稳定（保持后端返回顺序）、无时间字段排最后 | 用当前实现跑必须**变红**（先自证），修好后才绿 |
| G2 | 独立脚本 `scripts/check-messages-order.mjs`（**不进** `gate-all`） | 扫真实数据根（或 `--fixture`），逐群用生产函数 `buildMessages` 合并后检查逆序对；打印逆序的两条（时间、来源、groupId） | 发现逆序即非零退出；输出能直接定位「哪些群已经乱了」 |
| G3 | 契约门禁 | ①`docs/03` P3 条款写明排序规则（按绝对时间升序、最新在底部、无绝对时间时不可跨日比较）②静态断言：`messageSortValue` 必须使用绝对时间字段 | 文档缺条款或代码退回当天毫秒 → 红 |

### 边界

- 不改排序实现（用户明确「先不修」）
- 不改 `docs/`（文档由 Lead 维护）；G3 的静态断言只读代码，不写文档
- 不提交、不推送；完成后由 Lead 复核并提交

### 实测补充（用户 2026-11-10，决定性）

| 发送值 | 结果 |
|---|---|
| `max_tokens = 65536`（= 上游声明上限） | **400 `max_tokens 不能超过 65536`** |
| `max_tokens = 65535`（= 上限 − 1） | **成功**（用户直接在宿主模型设置里把「最大输出 token 数」改成 65535 实测通过） |

⇒ 上游边界是**排他**的："不能超过 65536" 实际语义是「必须 < 65536」。
⇒ 因此正确修法不是"撞到 400 再减一重发"，而是**夹取阶段就用 `learned - 1`**：
   正常请求根本不该先付出一次 400 的代价。

**据此定稿 B11d**（用户 2026-11-10 明确"必须撞到再减"）：

每个模型的上限不一样，只有撞到 400 才知道这次的值；所以流程必须是：

1. 先按 `min(configured, effective ?? learned ?? requested)` 发**本次尝试值**
2. 撞到 400 → 解析出该模型的声明上限 `learned`
3. **重发一次 `learned - 1`**（边界排他；不砍比例，避免无谓截断）
4. 成功 → 把 `effective = learned - 1` 按 **（群, 模型）** 落盘到 `limits.json`
5. 下一个请求起直接发 `effective`，**不再撞 400**

**存储：只在内存里记，不落盘**（决策：撞到即学、秒级完成，落盘只会带来缓存失效与维护成本）。进程重启后每个（群, 模型）最多再撞一次 400。
`capMaxTokens` 取值顺序：`configured → effective(内存) → learned(内存)`（配置人工指定优先）。

护栏：每次请求最多重发 1 次；`learned - 1 < 256` 时不重发；`learned - 1` 必须严格小于本次尝试值。

## B11c：`max_tokens` 撞上限取证（只加日志，不改语义）

**依据**：`docs/23` O-2。线上复发实例：目标 `agnes-3.0-flash@agnes2` 的请求返回
`400 {"message":"max_tokens 不能超过 65536 …","type":"AgnesAI_error"}`。

**当前缺口**：请求行不记录本次请求的 `max_tokens`，所以无法从历史数据判断「requested 与 learned 是否相等」，
也就无法判定 `attempt-limits.js:54` 的 `<=` 是否真的放过了「等于上限」的场景。

**本批只做**：
- `attempt-limits.js` 在解析到上限时打一条结构化日志：`group` / `model` / `requested` / `learned` / `equal` / `retried` / `next`（是重发还是原样返回）
- 不改任何判断分支，不改返回值

**验收**：单测断言「撞上限必产生一条日志且字段齐全」；真机复现一次 400 时日志里能看到 requested 与 learned。

## B13：abort 后流不结束（既有缺陷，门禁超时后暴露）
